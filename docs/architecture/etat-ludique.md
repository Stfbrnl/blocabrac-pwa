## Ludic-state migration (`docs/plans/PLAN-etat-ludique-hors-users.md`) — code-complete, prod field deletion still pending

The four fields that used to live on `users/{uid}` (`weeklyGoalItems`, `wallCounts`, `rouletteChallengesCompleted`, `rouletteRecentChallenges` — the last one 10 objects each carrying a full resolved label) now live in `user_ludic_state/{uid}` only. `services/ludicState.ts` (`getLudicState`/`updateLudicState`/`incrementRouletteCompleted`) is the only file that reads/writes this collection — every call site (`ClientDaily.tsx`, `ClientScreen.tsx`, `ClientStats.tsx`) goes through it, and `classementFlushWrites.ts`'s `wallCounts` write targets `user_ludic_state` inside the same read-then-write transaction as `classement_profiles`/`challenges` (`userLudicRef`, same "reads before writes" discipline as always). `firestore.rules` opens `user_ludic_state/{userId}` to its owner only (confirmed no staff screen reads these four fields). Verified against the emulator via `e2e-daily-flow.mjs`/`e2e-challenges-flow.mjs`, both green.

**Rollout status: ✅ COMPLETE (03/10/2026)**. Passe C (`users` no longer written/read for these four fields) deployed to prod in V2.61 (12/09/2026); the purge of the 16 legacy copies ran on 03/10/2026 and `purge-legacy-ludic-fields.js` now reports **0 candidate accounts** in prod. Sequence actually followed, in this order: rehearse on one account (`--uid`, the only candidate anyone could log into — all 16 were real climbers, no test account carries these fields since they all postdate Passe C), open the app on it, then the fifteen others (17 fields over 16 accounts, matching the prediction written beforehand), then the one explicit derogation. Verified account by account afterwards: **0 field lost in `user_ludic_state`**, whose `updated_at` never moved during the whole operation. `firestore.rules` needed no change, checked rather than assumed — the four fields appear nowhere in it (one comment aside) and the locked keys on `users` are only `inscritAuxCours`/`inscritAuxCompetitions`/`role`/`roles`/`levelOverride`. Backup of all 16 accounts' pre-purge `users` values: `firestore-migration/dump-ludic-legacy-2026-10-02.json` (gitignored folder). ✅ **The §7 measurement is done (03/10/2026)** — figures and method in `docs/plans/PLAN-etat-ludique-hors-users.md` §1, via the new read-only `scripts/measure-users-collection.js`. **~10 Ko** of network transfer for the `users` query at 61 accounts, 19.29 Ko of serialized JSON server-side, and the *live* ludic state would be **19.1 %** of that payload had it stayed. The gain measured on the purged (frozen-since-12/09) copies was only 8.4 %, i.e. below the 10 % threshold the plan set for deprioritizing itself — the counterfactual is the figure that answers the question, because what the chantier removed is the share that **grows with usage**, not with account count (30 accounts carry live ludic state vs the 16 that still carried legacy copies). Two method errors worth not repeating, both mine: the "before" measurement was never taken *before* purging (recovered byte-exact from the backup — luck, not method), and **clearing the network log before navigating destroys the very row to observe**, since Firestore keeps one long-lived WebChannel connection opened at startup and documents arrive on that already-established stream. There is no "users query" row to read in DevTools; the only working method is the **delta of total transferred** across the navigation, log *not* cleared. A cleared-log reading gave 0.2 Ko, an artifact — though a useful one: 0.2 Ko over 14 requests proved the 23.8 Ko `AdminUsers-*.js` chunk is service-worker-served, not fetched, so the 10 Ko is all Firestore.

⚠️ **`scripts/backfill-ludic-state.js` is a deploy-window catch-up tool, not a script to rerun by reflex** — its only job is recovering accounts touched by the *old* code (which only wrote `users`) during the Passe A→C transition. **Hardened 17/09/2026** after a review (`docs/handoffs/HANDOFF-ludic-state-backfill-simulation-2026-09-17.md`) found it would silently overwrite in *either* direction: rerunning `--fix` after Passe C is live could regress an account whose `user_ludic_state` had moved *ahead* of the frozen `users` snapshot (real climber activity via the now-live new code) back down to the stale value — confirmed as a live risk, not hypothetical, on a real prod account found via manual investigation the same day. Fixed structurally, mirroring `purge-legacy-ludic-fields.js`'s own directional guard (never delete a field absent elsewhere) read in the opposite direction: **the script now only fills a `user_ludic_state` field that is currently absent — it never overwrites a field that already exists there, even with `--fix`**, regardless of which value is "newer". A field present on both sides with a differing value is logged as guarded/skipped, never silently resolved either way — safe to leave for manual inspection. This also fixed the diagnostic noise: the pre-hardening equality check compared via raw `JSON.stringify`, which produced 10 false positives out of 11 flagged accounts in the 17/09 investigation purely from Firestore's unstable map key ordering (`wallCounts`) — the comparison now canonicalizes object key order recursively while preserving array order (`rouletteRecentChallenges` stays order-sensitive, correctly). Verified against the emulator (an absent field gets filled, a present-but-different field is never touched) before trusting the new logic against prod. 🔴 **"Safe to rerun at any time, by construction" was wrong, and following it would destroy user data — do NOT run `backfill-ludic-state.js --fix` again** (found 02/10/2026). The 17/09 hardening protects against overwriting a *newer* value; it does **not** protect against refilling a field the climber **deliberately deleted**, because an absence and a never-migrated field look identical — there is no tombstone. `weeklyGoalItems` is the one of the four that the app can delete (`ClientScreen.tsx` calls `updateLudicState(uid, { weeklyGoalItems: deleteField() })` in both `handleRemoveAllGoals` and an empty `handleSaveGoal`); the other three are only ever incremented or appended. Confirmed on a real prod account: `users.weeklyGoalItems` still holds two frozen `type:'boulder'` goals, `user_ludic_state` (written 01/10, carrying the other six fields) has none — the climber removed their weekly goals after 17/09. A backfill would hand them back. **Correct order for whoever finishes this**: run the purge's **simulation** first, treat any "jamais migré" warning as *investigate*, not as *run the backfill*; for a field deleted downstream the truth is the absence, so it must be purged, not refilled — which needs an explicit derogation since the purge guard refuses it by design (see `docs/handoffs/HANDOFF-purge-etat-ludique-2026-10-02.md` §4). **That derogation now exists (03/10/2026): `purge-legacy-ludic-fields.js --purge-unmigrated <uid>.<field>`**, repeatable, and deliberately with **no bulk form** — it must name each uid+field couple by hand, because the judgement it encodes ("this absence is the truth") can only be made account by account. The same pass made the script distinguish the two cases it used to lump together: **no `user_ludic_state` document at all** is a certain "never migrated" (the `users` copy is the only one in existence — the script refuses it *and* refuses to suggest the derogation), whereas **a living document missing just that one field** is the ambiguous, probably-deleted-downstream case, reported with the document's `updated_at` so the judgement can be made from the warning line itself. `--uid <uid>` already existed (since V2.61, contrary to what the 02/10 handoff's §4 bis claimed) and a mistyped uid now fails loudly instead of printing a reassuring "0 candidate". Write path exercised on the emulator over three seeded accounts (migrated / deleted-downstream / never-migrated) before any prod run, since a simulation only ever exercises the read-and-compare path. `roulette.ts` stays a pure module with no Firestore import.
- **Wall traversals scale with level (V2.55)**: catalog entry `G32`'s label is the literal placeholder `{traversée}`, resolved at draw time by `formatTraverseeLabel(traverseeConstraintForLevel(userLevel))` (both pure, unit-tested) into `resolvedTraversee` on `DrawResult` — jaune/vert/bleu → 1 wall; violet → 2 consecutive; rouge → 3; noir → 3 consecutive, no yellow holds; blanc → 4 consecutive, no yellow; rose → 4 consecutive, no yellow/green (barème given by the user 2026-09-06). `RouletteDialog.tsx` substitutes `{traversée}` and hides the "Niveau visé" colour chip for a traversal (no target colour). `G33` ("le grand tour") is unchanged.
- **New family-E entry `E35` "pieds libres" (V2.55)**: a max+1 boulder you may foot on any other boulder's holds — family E, so **no write** to `client_boulder_results` (assisted send of an above-level boulder).
- **Family E (progression) never writes to `client_boulder_results`**: on a max+1 boulder the proposal only asks for a partial attempt (three moves, isolate the crux move, etc.). Writing a partial attempt to `client_boulder_results` would corrupt classement/badges/auto-level, exactly like a real validation would. Since V2.55 the "J'ai relevé le défi" button *does* fire for family E too, but it only ever touches `users.rouletteChallengesCompleted`/`rouletteRecentChallenges` (the playful counter above) — never `client_boulder_results`.
- **"Déjà validé" filtering is session-scoped, not full-history**: `validatedBoulderIds` is derived from `successResults` (already in React state for boulders opened this session) rather than an extra Firestore read — a deliberate trade-off to keep the draw free, at the cost of family A/F not knowing about validations from a previous session. Families B, C, E are exempt from this filter entirely (repeating a known boulder is the point); F stays filtered (flash/no-fail only make sense on a boulder not yet mastered). **The catalog text must never promise more than this mechanism can deliver** — A2 originally read "un bloc que tu n'as jamais validé" ("never validated"), a promise the app can't keep since it only knows this session's validations; flagged by ClaudeNav (2026-08-18) as a trust issue, not a bug, and fixed by rewording to "pas encore fait aujourd'hui" ("not yet done today") — same mechanism, honest phrasing. A5 had the identical issue and got the same fix. Any future catalog entry referencing "already done"/"never done" must phrase it as "today", not "ever".
- **Empty-pool widening never errors**: if no boulder matches the target color, `drawProposal` widens first to neighboring colors, then re-admits already-validated boulders, then falls back to any active boulder — surfaced to the user as `widened: true` ("tu as déjà fait le tour…") rather than a dead end.
- **Wall counter prerequisite (`users.wallCounts`)**: family D ("murs délaissés") and the traversal entries in G need to know which walls a climber visits least. `boulders.wall` already existed (populated per-wall since `DailyBoulderForm.tsx`'s URL-scoped management screens) — the only real prerequisite was a per-wall incremental counter, added on `users/{uid}.wallCounts` (deliberately **not** on `classement_profiles` — a mirrored doc should only ever carry what a reader other than the owner consumes, see the `classement_profiles` mirroring section above; `wallCounts` has exactly one reader, the owner's own next roulette draw). It's updated the same way `classement_profiles.colorCounts` already is: a `wallById` map parallel to `colorById`, a `pendingWallDeltaRef` accumulated in `applyClassementDelta`, flushed in the *same* debounced `runTransaction` as `classement_profiles` (two documents, one atomic transaction) — no new write path, no new Firestore rule (a client can already `update` any field of their own `users` doc except the small locked-keys list). **Deliberately has no reconciliation script**, unlike `colorCounts`: the field is private and purely playful (it only steers which wall family D suggests), with no classement/badge derived from it — a drift here is a mistargeted suggestion, not a data-integrity issue.
- **Wall circuit order**: `config/gymConfig.ts`'s `walls` array is ordered to match the gym's actual physical circuit (confirmed with the user 2026-08-18), not the historical add-order it used to have — every consumer (`ClientDaily.tsx`'s wall picker, `DailyBouldersList.tsx`, etc.) reads the same array, so this was a pure reorder with no schema change.
- **"Roulette de la mort"**: a separate button/draw (`drawDeathProposal`), always max+1 with **no ceiling fallback** — returns `null` (shown as "pas de bloc disponible") rather than silently rebasing to max, since its whole appeal is rarity; also exempt from the anti-lassitude memory (see below), on the same rationale. **`DEATH_PROPOSAL`'s text was rewritten in V2.55** (the old "the whole max+1 boulder, nothing added" was too hard for anyone to actually play): now a max+1 boulder the climber sends while allowing themselves 1–2 extra holds of their choice anywhere on the wall (hands or feet, any colour). Still family E → still no write. `drawDeathProposal`'s logic is unchanged, only the label.
- **Anti-lassitude, not in Firestore**: the ~10 most-recently-drawn proposal ids live in `localStorage` (`${storageKeyPrefix}_roulette_recent`), read/written by `ClientDaily.tsx` around the call to `drawProposal` — `roulette.ts` itself never touches `localStorage`, staying a pure function of its inputs (this is also what makes it trivially unit-testable with an injectable `rng`).
