## Boulders: one collection, several lifecycles

All climbing routes (daily wall routes and competition routes) live in a single `boulders` collection, discriminated by `type: 'daily' | 'competition'`:

> ⚠️ **Never delete a `boulders` document.** Deactivation (`is_active: false`, set by `DailyBoulderForm.tsx`) is the *only* retirement path — a wall rotation never removes docs (grep-verified V2.54). The monotonicity of both the all-time **and** the season classement scores depends on this: since V2.56 the reconciliation counts a validation as long as its boulder doc exists (at the boulder's last-known colour), so a hard delete would make every associated validation — and its points — vanish at once. `client_boulder_results`, `client_badges`, and every stats/classement page also assume the doc stays readable forever. If a test/mistake boulder must go, deactivate it; a manual delete from the Firebase console is a data-integrity break, not a cleanup.


- **Daily boulders** (`type: 'daily'`): managed per-wall in `Ouvreur/DailyBoulders/`, shown to clients in `Client/Daily/ClientDaily.tsx`. Color (`color` field) is always visible. `is_child_route: boolean` marks a "ouistiti" route (children's route physically marked with a monkey icon instead of the color logo) — it exists across the full color range, it is not a separate color.
- **Official "grosse compétition" boulders** (`type: 'competition'`): created via `Ouvreur/CompetitionBoulders/CompetitionBoulderForm.tsx`, tied to a `competitions` doc via `competition_id`. Their real cotation (`difficulty` field) is hidden from climbers during the event — the validation screen (`Client/Competitions/ClientCompetitions.tsx`) never displays it, climbers just mark success/attempts blind ("Mystère"). Scoring reads `difficulty` live.
- **Reused daily boulders in a "compétition régulière"**: a level-restricted competition (via `minLevel`/`maxLevel` on the `competitions` doc) that runs for weeks on walls that are never stripped, built from *existing* daily boulders instead of new hidden ones. These boulders stay `type: 'daily'` forever and gain `competition_id` + `competition_active: true` while tagged in. `competition_active` is the field that matters here — it's what distinguishes "currently an active member of this competition" from a boulder that merely still carries an old `competition_id` for historical stats. **`competition_id` is never cleared** once set (on either boulder kind) — every stats/classement page reconstructs a competition's results by querying boulders on `competition_id` alone, with no `type` filter.
- "Terminer la compétition" (`Ouvreur/CompetitionBoulders/CompetitionBouldersList.tsx`) ends a competition's boulder lifecycle: `type:'competition'` boulders become `type:'daily'` (their hidden cotation becomes the public `color`, to be re-graded from climber feedback); reused daily boulders just lose `competition_active`. The competition's own `status` field is a separate, manually-controlled admin action — this button never touches it.


## Boulder images: Cloudinary, `image_public_id` first, `image_base64` as fallback

Boulder photos are uploaded to Cloudinary (unsigned preset, folder `blocabrac/boulders`) instead of stored as base64 in Firestore — the free Spark plan's 10 GiB/month egress quota can't survive serving inline images to every wall view. `services/imageStorage.ts` is the **only** file allowed to import/call Cloudinary (`uploadBoulderImage`, `getBoulderImageUrl`, `deleteUnconfirmedUpload`) — swapping providers later means rewriting only that module. New boulders write `image_public_id`; the legacy `image_base64` field is never written again but is kept as a read-time fallback (`image_public_id ? getBoulderImageUrl(...) : image_base64`) wherever a boulder image is rendered — every such site must implement both branches, a screen that only checks one will show broken images for the other kind of boulder. `getBoulderImageUrl(publicId, 'thumb' | 'full')` composes the URL from Cloudinary transformation strings (`f_auto,q_auto,w_400`/`w_1000`) rather than storing pre-built URLs, so there's nothing to keep in sync if the transformation recipe changes.

The annotation dots (start/end holds) are baked into the image raster at save time (`canvas.toDataURL()` in `DailyBoulderForm.tsx`/`CompetitionBoulderForm.tsx`) — the `annotations` field in Firestore is write-only after creation (read back only when re-editing that same boulder), never used to render an overlay at display time. This is why the Cloudinary upload happens at submit time, not on file selection: the final image doesn't exist until the ouvreur has finished placing the dots, so "upload immediately to hide latency" isn't compatible with baking annotations into the raster. Editing an existing boulder without picking a new photo skips the upload entirely and leaves `image_public_id` untouched (Firestore `updateDoc` only touches keys present in the payload).

`firestore-migration/migrate-boulder-images-to-cloudinary.js` is the one-time backfill for boulders created before this change: Passe A (default) uploads existing `image_base64` to Cloudinary and writes `image_public_id`, keeping the base64 as-is; Passe B (`--delete-base64`, run manually later after visual verification in prod) removes the now-redundant base64 field.

`scripts/cleanup-orphan-boulder-images.js` runs monthly via `.github/workflows/cleanup-orphan-boulder-images.yml` (cron + `workflow_dispatch`) to delete Cloudinary images no longer referenced by any `boulders` doc. It lives in `scripts/` (tracked by git) rather than `firestore-migration/` (entirely gitignored) specifically so `actions/checkout` in CI actually has the file to run — a script that only exists locally can't be checked out on a fresh CI runner. It deliberately queries `boulders` with **no filter** on `is_active`/`type`/`competition_active` — a deactivated boulder (`is_active: false`) or one whose competition ended still keeps its image referenced for historical stats, and a filtered query would wrongly treat that image as orphaned. Guardrails: dry-run unless `--delete`, never touches a Cloudinary resource younger than 7 days, and aborts if the reference count drops both more than 20% **and** by at least 20 references versus the last run (likely a partial read or auth failure, not real deletions) — both conditions must hold so a legitimate sector rotation (one wall's ~15 boulders pulled at once) doesn't trip it at low total boulder counts; `--force`/`--accept-drop` bypasses the abort explicitly when the drop is legitimate, instead of hand-editing the state file. If `cleanup-state/state.json` doesn't exist yet (first run, or a lost file), the guard is skipped with an explicit log line rather than silently — there's nothing to compare against. That comparison's state lives in `cleanup-state/` (also tracked by git) because it must survive across ephemeral CI runs; the workflow commits it back after each execution. Credentials come from env vars in CI (`FIREBASE_SERVICE_ACCOUNT_JSON`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` — GitHub secrets) or local gitignored files in `firestore-migration/` when run manually from the Codespace (`serviceAccountKey.json`, `cloudinary-admin-credentials.json`). **`state.json`/`orphan-images-log.json` are emulator-aware** (V2.51, extending the same fix from `reconcile-classement-profiles.js` — see the `classement_profiles` section below): both paths derive from `FIRESTORE_EMULATOR_HOST`, writing `*.emulator.json` (gitignored) instead of the tracked production files whenever it's set — the risk here is sharper than for the reconciliation log, since `state.json` is exactly what the drop-guard above compares against.

`--backup <dossier>` (same script) downloads every currently-referenced Cloudinary image to a local folder — idempotent (skips files already present, matched by sanitized public_id regardless of extension) and writes a `manifest.json` mapping `public_id → boulder_id → filename`. Exists because since Passe B removed `image_base64`, each boulder photo's only copy lives on a free-tier third-party account with no backup of its own. Manual/occasional use only for now (not wired into the CI workflow) — where to store the archive durably is still an open decision, deferred until the multi-gym (white-label) push where the volume will actually matter.


## First ascents (`boulders/{id}.firstAscents`) — a capped list, not a counter, V2.61

`docs/plans/PLAN-premiers-ascensionnistes.md`: on a hard-colour boulder (`gymConfig.firstAscentColors`, currently `['noir', 'blanc', 'rose']`), the first five climbers to validate it are shown on its detail card, in order, with their first-validation date. **Cost: ~0 extra reads, ≤5 writes per boulder over its whole life** — the list lives directly on the boulder document (`boulders/{id}.firstAscents: {uid, displayName, at}[]`), already loaded by `ClientDaily.tsx`; querying `client_boulder_results` instead was rejected outright (blocked by rules — a client can't read another client's results, that's the whole reason `classement_profiles` exists) and a `boulders/{id}/first_ascents/{uid}` subcollection was the fallback if the rule below turned out infeasible (5 reads per card open instead of 0).

- **Consent is a dedicated field, not `classementOptIn`** — `firstAscentOptIn: boolean` (default `false`), stored in `user_ludic_state/{uid}` (the ludic-state migration above was already in flight when this was built, so it went straight to the new collection rather than adding another line to `users`), toggled in `ClientProfile.tsx`. Evaluated only at validation time — enabling it later never backfills past validations, and the UI says so.
- **Firestore rules enforce append-only integrity, not just size** — the naive approach (`request.resource.data.firstAscents == resource.data.firstAscents + [newEntry]`) does **not work**: Firestore's rules language has no list concatenation operator (`"Unsupported operation error: list + list"`, confirmed on the emulator — a real dead end, not a hypothetical one). The working alternative, `isAppendOnly4()` in `firestore.rules`, unrolls the comparison into up to 4 individual indexed equality checks (`newList[0] == oldList[0]`, …) — since the list is capped at 5, the existing prefix before any single write is at most 4 elements long. This is what makes the list **actually tamper-proof**: a client can add their own entry at the end, but cannot rewrite, reorder, or drop any earlier entry, cannot add another uid's entry, and cannot write once the list already has 5. Add a 5th unrolled index (and bump the cap check) if `FIRST_ASCENT_LIST_MAX` ever changes. A client update is also confined to `type == 'daily' && !competition_active` (never on a hidden-cotation competition boulder — see the boulders lifecycle section above) and `diff().affectedKeys().hasOnly(['firstAscents'])`; staff (ouvreur/admin) keep unrestricted write access, unchanged.
- **The write is immediate, never debounced** — triggered by the "Réussi" click, already immediate, and happens at most once per boulder per climber. It does **not** share `ClientDaily.tsx`'s debounced classement/wallCounts/challenges transaction; it's its own small `runReadThenWriteTransaction` (`utils/firstAscentWrites.ts`'s `buildFirstAscentWrite`, pure, same "reads before writes" discipline as `classementFlushWrites.ts`) that re-reads the boulder doc fresh at write time — never the boulder's in-memory copy in `ClientDaily.tsx` state, which could be stale if another climber just took the 5th spot. `shouldRecordFirstAscent()` (`utils/firstAscents.ts`, pure, unit-tested) centralizes the six preconditions (success, opt-in, eligible colour, `type:'daily'` non-competition, list not full, uid not already present); a failure here is caught and logged to console only — the boulder validation itself already succeeded by this point, and missing a prestige-list slot must never surface as a user-facing error on an otherwise-successful validation.
- **Withdrawal isn't retroactive by itself**: turning `firstAscentOptIn` off doesn't remove a name from lists it's already on (frozen in each boulder doc, nothing scans the whole collection to find it). `scripts/purge-first-ascent-entry.js` (dry-run by default, `--fix`, requires `--uid`) removes every occurrence of a given uid on explicit request — on-demand only, no cron, since there's no periodic drift to correct here, only an occasional real request.
- **A deactivated boulder keeps its list** — consistent with the project's "never delete a `boulders` doc" invariant (V2.56): the list becomes a small standing "palmarès" of a retired wall rather than disappearing with it, at zero extra cost since the document was never going away anyway.
- Verified end-to-end against the emulator, not just via rules tests: `test/e2e-first-ascents-flow.mjs` + `test/seed-first-ascents-users.mjs` — two real climbers filling a boulder's list from 3/5 to 5/5 in order, then a third climber validating on a full list, asserting the write is silently rejected (their own boulder validation still succeeds) and the list stays untouched. This is the one property that bounds the whole feature's cost, hence the one locked by a test.


## Boulder attribution: `openedBy` (who opened it) vs `created_by` (who entered it), V2.65

`docs/plans/PLAN-ouvreur-createur-bloc.md`: `boulders/{id}.openedBy: {uid, displayName} | null` records which ouvreur physically opened the route, distinct from the pre-existing `created_by: string` (uid, automatic, set once at creation and never overwritten on edit) which only records who typed it into the app. Built because staff sometimes enter a colleague's route the same evening without wanting to steal their credit — a gym-management need, not a data-model quirk. **Never conflate the two fields** — `created_by` stays the automatic paper trail of who used the form, `openedBy` is the deliberate, editable attribution chosen from a menu, defaulting to the logged-in user when they themselves hold the ouvreur role.

- **Denormalized, like `firstAscents`/`classement_profiles`** — `displayName` is frozen at write time because a client cannot read `users` for another uid; a later name change on the ouvreur's own account does not retroactively update past boulders. `null` is a valid, common value (old boulders, boulders with no confirmed opener) and every reader must render it without an error message, not a placeholder that looks like a bug.
- **Menu is built from the *live* ouvreur roster, not a frozen list** — `utils/staffAccounts.ts`'s pure `buildOuvreurOptions()` merges the two `role`/`roles[]` queries (the project's standard two-branch pattern, see `MessagesList.tsx`), deduplicates by uid, and falls back name → email → uid. An ouvreur who leaves the role simply stops appearing as a future choice; their name stays frozen on blocks already attributed to them (same rationale as `firstAscents`' unlinked uid). Fetched once per form mount (`DailyBoulderForm.tsx`, `CompetitionBoulderForm.tsx`), independent of the wall/competition being edited — not re-queried per boulder.
- **Editable after the fact, unlike `created_by`** — the whole point is letting a later correction reassign a wrongly-attributed boulder; the `<Select>` is a normal controlled field on both creation and edit forms.
- **Never shown while a competition boulder's cotation is still hidden** — `type: 'competition'` boulders never display `openedBy` (neither in `ClientCompetitions.tsx`, which doesn't read the field at all, nor anywhere reachable during the event); it only becomes visible once "Terminer la compétition" converts the boulder to `type: 'daily'` and it's rendered through the normal `ClientDaily.tsx` path. Decided explicitly (unlike the hidden `difficulty`, the opener's name reveals nothing about difficulty — but the staff still preferred to hold it back until after the event).
- **No consent toggle** — decided explicitly against a `firstAscentOptIn`-style opt-in: an ouvreur signing their own work is assumed by default, unlike a climber's own validation history.
- **Firestore rules validate the uid, not the honesty of the choice** — `isValidOpenedBy()` (`firestore.rules`) short-circuits to `true` when the field is absent/`null` (no extra read on the common case), and otherwise calls a uid-parameterized `hasRoleUid(uid, "ouvreur")` (a variant of `isUserRole()` for an arbitrary uid, not just `request.auth.uid`) to reject an invented or non-ouvreur uid. It cannot and does not try to stop an ouvreur from mis-attributing a real colleague's account — that's social control, sufficient at gym scale, same doctrine as the rest of the project's permission model. The `update` rule only pays this extra `get()` when `openedBy` is actually part of the write's diff (`affectedKeys().hasAny(['openedBy'])`), so editing a boulder's color/instructions stays at its pre-V2.65 read cost.
- **Broadening who can enter blocs (to cover an absent ouvreur) also broadens what they can read** — the ouvreur role already grants read access to `client_boulder_results`, `competition_participants`, `competition_results`, and the nominative competition-classement tab. This is a pre-existing, already-accepted status quo (confirmed again 17/09/2026, first raised 14/08) — not something this feature changes, but something anyone distributing the ouvreur role more widely to enable this feature should know.


## Opener's note (`boulders/{id}.openerNote`), V2.66

`docs/plans/PLAN-anecdote-methodes-missions.md` §A: a free-text field the ouvreur fills in — movement intent, a name given to the boulder, a warning (*"Mouvement inspiré de Fontainebleau, attention au rétablissement."*). Extends V2.65's `openedBy` the same way: `openedBy` says **who** opened it, `openerNote` says **what they had in mind**. Same "appears only if filled in" doctrine as `openedBy`, same competition-boulder hiding (automatic — `ClientCompetitions.tsx` never reads the field), same both-forms discipline (`DailyBoulderForm.tsx` and `CompetitionBoulderForm.tsx`). **Capped at 300 characters**, enforced both client-side and in `firestore.rules` (`isValidOpenerNote()`, no `get()` needed so applied unconditionally on every staff write, unlike `isValidOpenedBy()` which is gated behind `affectedKeys()` to avoid paying its `get()` on unrelated edits) — `boulders` is loaded in bulk per wall, so an unbounded note would reproduce exactly the cost problem that pushed boulder images out to Cloudinary.


## Method log (`carnet de méthodes`) — `boulders/{id}.methodCounts`/`methodVotes` + `client_boulder_results/{id}.methods`, V2.67

`docs/plans/PLAN-anecdote-methodes-missions.md` §B: climbers vote which technique(s) they used on a boulder (heel hook, crimp, dynamic move...) from a **fixed vocabulary** (`gymConfig.ts`'s `climbingMethods`, 8 entries, `value` keys mirrored verbatim in `firestore.rules`' `methodVocabulary()` — keep both in sync by hand), up to `MAX_METHODS_PER_VOTE` (3), shown to every climber once a boulder has ≥ `METHOD_VOTES_DISPLAY_THRESHOLD` (3) votes (`utils/methodVote.ts`'s `summarizeMethodVotes` returns `null` below the threshold — the UI renders nothing rather than a misleading "100%" on a single vote).

- **Two writes, one atomic transaction, by design** — a naive single counter on `boulders` can't tell who already voted (nothing would stop 50 clicks from one account). The vote itself lives on the climber's own `client_boulder_results/{uid}_{boulderId}.methods: string[]` (their own document, already written at validation); the aggregate lives on `boulders/{id}.methodCounts`/`methodVotes`. `utils/methodVoteWrite.ts`'s `buildMethodVoteWrite` (pure, no Firestore import) reads both documents fresh via `runReadThenWriteTransaction` and writes only the touched `methodCounts` keys as a patch (not the whole map — no orphan-key risk here, the vocabulary is fixed forever, unlike `colorCounts`).
- **Reconciliation (V2.71, `docs/handoffs/RETOUR-v2701-v2702.md` §2)**: `methodCounts`/`methodVotes` were the last incremental counters with no safety net. `scripts/reconcile-method-counts.js` recounts them from `client_boulder_results.methods`.
  - Expected value for each boulder: `methodCounts[m]` is the number of result docs whose `methods` contains `m`; `methodVotes` is the number with non-empty `methods`. A vote left on a cancelled success still counts. A key at 0 is equivalent to an absent key.
  - Dry-run by default, `--fix` to write. Same drift guard as the classement reconciliation (more than 30 % **and** at least 3 boulders aborts; `--force` overrides).
  - Monthly via `.github/workflows/reconcile-method-counts.yml`. Console-only journal, no tracked state file.
  - Emulator regression test: `frontend/test/reconcile-method-counts-emulator.mjs`.
  - `canEraseFailure`'s "no method vote" guard is **client-side only**: `firestore.rules` lets the owner delete their own result. Keep the guard anyway; it avoids creating drift instead of repairing it monthly.
- **Only ever shown for `type: 'daily'` non-competition boulders** — same rationale as `firstAscents`/`openedBy`: the method used reveals something about difficulty, which stays hidden during a "grosse compétition". Automatic by construction (`ClientDaily.tsx` only loads `type=='daily'`) and defensively re-checked in `firestore.rules`.
- **Modifiable**, not append-only: reopening a boulder's validation and changing the ticked methods decrements the old ones and increments the new ones (`utils/methodVote.ts`'s `computeMethodVoteDelta`), `methodVotes` itself only moves when a climber transitions into or out of "has voted at all" (0 methods ⇄ ≥1 method).
- **⚠️ Firestore rules `get()` inside a transaction sees the state from BEFORE that transaction, never a sibling write made earlier in the SAME transaction** — verified empirically on the emulator (not assumed), see `firestore.rules.test.ts`'s `describe('boulders : methodCounts / methodVotes ...')`. This is what makes `isValidMethodVoteUpdate()` possible at all: the `boulders` update rule calls `get()` on the voting client's own `client_boulder_results` doc to read their **pre-transaction** vote, and validates that the `methodCounts` delta this write applies is consistent with that (a `+1` on a method the climber didn't already have, a `-1` on one they did, never more than one step, never more than 3 net additions) — a client cannot inflate the aggregate or erase another climber's vote, because the check is anchored to the voter's own prior state, not to anything the current write claims. Any future feature that wants a rule to cross-validate two documents written together in one transaction should re-read this test before assuming either "before" or "after" semantics — it's not obvious, and guessing wrong here would have silently opened a real integrity hole.
- Also fixed in passing: `handleValidateSuccess`/`handleRate` in `ClientDaily.tsx` write `client_boulder_results` via a bare `setDoc` (no `merge: true`, full-document replace) — before this chantier that was harmless because nothing else was ever written to that document, but it would have silently wiped a climber's method vote on their next re-validation of the same boulder. Fixed by explicitly carrying `methods` forward in both write payloads, the same way `createdAt` already was.


## Daily boulder results: the first success is the measure, a repeat is not (V2.69)

`docs/handoffs/RETOUR-bug-missions-et-revalidation.md` §2 ("B sans fenêtre", decided by the user 25/09/2026). The barème rewards few attempts because that signals difficulty *relative to the climber*, and that signal only exists at the first encounter. A wall lives six weeks and repeats typically happen three days later, so letting a repeat rewrite the result would make the classement converge to "1 attempt everywhere" and measure time spent repeating (inflation fed by M1/M3).

- **`utils/boulderResult.ts` (pure) + `ClientDaily.tsx`'s `writeBoulderResult` are the single write path** for `client_boulder_results` from that screen: `setDoc(..., { merge: true })` carrying **only** the fields the gesture controls (`planResultWrite`). Unchanged fields are never rewritten (structural preservation, §2.5), `createdAt` is carried from the stored doc, and the classement delta is applied after the write, only if the success/attempts state actually moved.
- **The dialog has three states**:
  1. **Already succeeded**: read-only, "Déjà validé le … en N essais", no "Réussi"/"Échoué" buttons.
  2. **"Corriger ma saisie"** (no time limit, §2.2): the only way to change the attempts of a recorded success or cancel it, and the classement follows.
  3. **Otherwise**: explicit attempts choice, then "Réussi"/"Échoué".

  `handleValidateSuccess` also re-checks the stored result itself and refuses to act on an already-succeeded boulder, so the rule doesn't rest on the UI alone.
- **A failure then a success is a FIRST success (§2.7)**: the rule is keyed on "already *succeeded*", never "already *entered*". It writes and counts normally (not a flash for M3, though).
- **No default attempt count (§2.4)**: the Select starts empty and "Réussi" is disabled until a value is chosen. The old `attempts[id] || 1` silently declared a flash.
- **Rating/comment/proposed grade are not scoring data**: they stay editable outside correction mode ("Enregistrer" → `handleSaveNotes`, which never writes `success`/`attempts`), and are prefilled from the stored result when the dialog opens (`handleOpenBoulder`, one read per boulder per session, cached).
- **Mission gestures never write a result** (§2.8): "J'ai testé ce bloc" (a max+1 boulder not yet succeeded, M4) and "Je l'ai refait" (an already-succeeded boulder) go through `recordMissionGesture` (a transaction re-reading `user_ludic_state`, outside the shared debounced flush, no optimistic UI). Each is shown only if it would actually advance the grid (`missionGestureAdvances`).
- **Button grammar (§2.9) — keep it for any future button**: a button that writes a result is a **state adjective** ("Réussi", "Échoué"). A button that never writes one speaks in the **first person, past tense** ("J'ai testé ce bloc", "Je l'ai refait", "J'ai relevé le défi", M4 bis's "Je l'ai fait"), is **outlined** with an icon, and carries the grey caption "n'enregistre pas de résultat". `ClientHelp.tsx` documents the three gestures (record / advance a mission / correct).
- **Known gap, not enforced by rules**: `firestore.rules` still lets the owner rewrite their own result freely. The rule is enforced by the UI and by `handleValidateSuccess`'s guard, which is sufficient under the project's trust doctrine and avoids a rules change that would also block legitimate corrections.
- **"Échoué" needs no attempt count, on purpose.** A failure scores nothing, so asking for a count would be friction for nothing. `attempts: null` is a legal stored state.
- **"Effacer cet échec" (V2.70.2)**. A stored failure closes M3 (flash) forever on that boulder, because `neverTriedBefore` requires *no* stored result. That includes a success later cancelled through "Corriger ma saisie". So a mis-clicked "Échoué" must be erasable.
  - What it does: `handleEraseFailure` **deletes** the `client_boulder_results` doc (rating/comment go with it, and the confirm dialog says so). The boulder becomes "never tried" again.
  - Refused while a method vote is still on the doc (`canEraseFailure` in `utils/boulderResult.ts`): `boulders.methodCounts` counts that vote, so deleting the doc would drift the aggregate.
  - It touches neither the classement nor the missions.
  - No new cheating power: a climber could already skip entering a failure.
  - Covered by step 10 of `e2e-weekly-missions-flow.mjs`.
