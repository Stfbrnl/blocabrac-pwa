## Bloc Roulette — a free, stateless daily-challenge draw

`utils/roulette.ts` (V2.44, see `docs/plans/CONCEPTION-roulette-et-defis.md` Partie 1) draws one proposal from a fixed 46-entry catalog (`CATALOG`) plus a separate "roulette de la mort" entry, shown via a 🎲 button on `ClientDaily.tsx`. **The module imports nothing from Firestore** — that's the property that makes the feature free, called out in its own header comment and worth preserving on any future edit: the draw and "relancer" never cost a read or write. Everything it needs (today's active boulders, the climber's `level`, `wallCounts`) is already in memory or read as part of an existing `getDoc` call.

- **Level weighting**: `pickLevelTarget` picks max−1 (~70%), max (~20%), or max+1 (~10%) of the climber's current `users.level`; `resolveTargetColor` handles floor (max−1 collapses to the current level) and ceiling (max+1 collapses to max, flagging `levelExcludedE` so family E — "réussite partielle" — never appears once a climber is already at the top color). D and G aren't a separate weighting axis — once a tier is picked, every eligible family at that tier (including D/G) competes in one uniform draw.
- **Level-dedicated / level-shifted proposals (V2.55)**: `Proposal` carries optional `minLevel`/`maxLevel` (inclusive `Level` bounds) — `drawProposal` filters the tier pool through `levelAllows(userLevel, p)` before the uniform draw, with a safety net that ignores the restriction if it would empty the pool entirely at that tier. Also optional `levelOffset` (a number, e.g. `-1`): the entry still lives in its `levelTarget` pool, but the resolved `{couleur}` is shifted that many extra rungs down `levelOrder` — used by the "grimpe à une main" / "adhérences forcées" drills that deliberately target two rungs below (safety + the constraint alone makes them far harder). The V2.55 batch of exercises adapted from **al-escalade.fr**'s "bloc" discipline (B36–B46, C44, G43): touché-collé feet, no-foothold smearing, two-finger grip, imposed technique (cancan/lolotte/heel-hook/contrepointe/flag, each defined in `details`), one-handed (`levelOffset -1`), both-hands-together (`minLevel: rouge`), 6×40s resistance (`minLevel: rouge`), 3 linked boulders read aloud (`minLevel: bleu`), plus two advanced-technique entries gated at `minLevel: blanc` — Yaniro/figure-4 and bat-hang start, technique explained via `Proposal.details` (rendered under the label by `RouletteDialog.tsx`).
- **"Trouve un bloc du bon niveau, ou compose-en un" reminder (V2.55)**: shown once by `RouletteDialog.tsx` under every colour-targeted draw (hidden for a traversée) rather than repeated in each catalog string — same "say it once in the dialog" approach as the "Niveau visé" chip.
- **"J'ai relevé le défi" completion tracking (V2.55, "version hybride")**: a `RouletteDialog.tsx` button on **every** family (E and the death roulette included — decided 2026-09-06; it replaced the old family-E-only "C'est fait" button) fires `onValider`, whose `ClientDaily.tsx` `handleValiderRoulette` does **one** `updateDoc` on `users/{uid}`: `rouletteChallengesCompleted: increment(1)` + `rouletteRecentChallenges` (a client-recomposed, `ROULETTE_RECENT_COMPLETIONS_MAX`=10-capped array of `RouletteCompletion` via the pure `addRouletteCompletion`). **Never writes `client_boulder_results`** — so a family-E "un cran au-dessus" completion counts without touching classement/badges/level (the E invariant is specifically about not faking a boulder validation, not about never writing anything). **Zero extra reads**: the `users` doc is already fetched at ClientDaily mount (level/`wallCounts`), and the wall/boulder picker options are already in memory. The optional wall+number the climber may enter is stored on the entry (declared, unverified — same "confiance" doctrine as the declarative families). No new collection (rejected: an unbounded history query), no rules change (`rouletteChallengesCompleted`/`rouletteRecentChallenges` aren't locked keys), no reconciliation script (same rationale as `wallCounts`: private, playful, a drift is harmless). Counter shown under the roulette buttons on `ClientDaily.tsx` and, with the recent list, in `ClientStats.tsx` (both already read that `users` doc). `resolveDrawLabel(result)` (moved from `RouletteDialog` into `roulette.ts`, pure) resolves the stored label.
  - **No optimistic UI** (ClaudeNav review 2026-09-06): `handleValiderRoulette` updates `selfProfile` (the visible counter) **only after** `updateDoc` resolves — a failed write shows an error and leaves the counter untouched, never a count that ticks up next to an error message. `nextRecent` is recomposed from `selfProfileRef.current` (a ref synced in an effect, not the render-closure `selfProfile`) so two quick completions in one mount can't make the second overwrite the first in the 10-list; the count uses a functional `setSelfProfile(prev => …)`.
  - **⚠️ This counter is 100% declarative for every family** — even "un bloc à ton niveau" is never verified. It must **never become the input of anything derived** (a badge, a level bump, a classement contribution): a "10 défis Roulette relevés" badge would be self-awardable in ten clicks and would re-open, sideways, exactly what the family-E invariant closes. `rouletteChallengesCompleted` is display-only, forever.
  - **e2e**: `test/e2e-daily-flow.mjs` (steps 6–7) drives the button (incl. the optional wall/number field) and asserts `users.rouletteChallengesCompleted === 1` + the `rouletteRecentChallenges` entry via `firebase-admin` — per `docs/processus/PROCESSUS-erreurs-avalees.md` §4 ("every incremental counter needs an e2e assertion on its resulting value"), this being the project's **third** such counter after `colorCounts`/`wallCounts`.
- **`users/{uid}` is read in full by every staff screen** (`getDocs(collection(db, 'users'))`, unfiltered — `AdminUsers`, `CompetitionStats`, `AdminCompetitionStats`, `AdminCompetitionRegistration`, `BoulderStats`, `CompetitionBoulderStats`), and the client SDK has **no field projection**. Only put identity/rights fields there: name, role, level, date of birth, registrations. **Any per-user state — counters, preferences, display history — goes in `user_ludic_state/{uid}`**, read/written only by its owner (`services/ludicState.ts` is the only file that imports this collection, same discipline as `imageStorage.ts` for Cloudinary).


## Défis entre potes — a `challenges` collection, built on top of Bloc Roulette's counters

`utils/challenges.ts` (V2.46, `docs/plans/CONCEPTION-roulette-et-defis.md` Partie 2) is a small pure module (winner/progress logic only, no Firestore import, same discipline as `roulette.ts`) backing a `challenges/{id}` collection: 2–6 friends (`friendships`, accepted only — the UI in `ClientFriends.tsx` only offers already-accepted friends as participants, there is no separate invite/accept dance for a challenge itself) race on one of four `structure`s (`seuil`/`fenetre`/`bloc_designe`/`declaratif`). `progress` is a single map field on the document (`{uid: {value, updated_at, confirmed_by?}}`), never a subcollection — the 6-participant cap is what keeps Firestore's ~1 write/sec/doc contention limit a non-issue, see the conception doc §2.3; **never raise that cap without revisiting the model**.

- **No push notifications anywhere in this app** (confirmed while designing this feature — there's no FCM, no service-worker push): a challenge is discovered purely by pull, the next time a participant opens "Potes de grimpe" (`ClientFriends.tsx`, where the whole feature's UI lives — not a separate top-level tile, deliberately, since participant selection needs the friends list already loaded there). A creator's challenge appears with all participants already inside it (consent = being friends already), no per-challenge accept step.
- **Three structures update from `ClientDaily.tsx` automatically; `declaratif` is the only one with a manual write from `ClientFriends.tsx`** (a "C'est fait" button, one `updateDoc` on `progress.{uid}` only — no verification, consistent with the whole app's "confiance donnée aux grimpeurs" doctrine already established for the seasonal classement and Roulette).
- **Same incremental-counter discipline as `classement_profiles`/`wallCounts`**: active challenges (`status: 'en_cours'`, `participants array-contains uid`) are loaded **once** at `ClientDaily.tsx` mount (`activeChallengesRef`, `getDocsCacheFirst`) and kept in memory — never re-queried per validation. `pendingChallengeDeltaRef` (cumulative delta, for `seuil`/`fenetre`) and `pendingBlocDesigneScoreRef` (best-score-seen, for `bloc_designe` — a max, never a sum, since that structure compares a single best attempt on one designated boulder) are accumulated in `applyClassementDelta` alongside the pre-existing score/color/wall deltas. ⚠️ **They are no longer flushed in the same transaction as `classement_profiles`/`wallCounts` (02/10/2026, `docs/URGENT-flush-bloque-par-challenges.md`)** — they were, and it cost real validations in production. The debounced flush now runs **two** transactions in order: ① `classement_profiles` + `user_ludic_state` (score, murs, missions — ce qui ne peut pas être perdu), then ② `challenges.progress` alone (`utils/challengeProgressWrite.ts`), whose failure is logged and goes no further. A challenge's progress is a bonus; a climber's score is not, and sharing one transaction made the second die with the first. The challenge transaction's failure is deliberately **not** re-thrown: re-queuing would make the debounce queue retry the whole pending and re-apply an already-written classement delta.
- **`seuil` only counts a challenge's `target_color`** — which since V2.53 may be a literal colour *or* one of two per-participant tokens `SEUIL_TARGET_MAX` / `SEUIL_TARGET_MAX_MINUS_1` (`utils/challenges.ts`): `ClientDaily.tsx`'s seuil branch resolves it against **that grimpeur's own** `users.level` at delta time via `resolveSeuilTargetColor(target, level, levelOrder)` (pure, unit-tested), so two climbers of different levels can run a fair challenge (each counts blocs of their own max / max−1 colour). Floor: max−1 collapses to the current level at the bottom of `levelOrder`; unknown level → the challenge simply doesn't advance for that participant. `firestore.rules` doesn't validate `target_color` so no rules change was needed; `resolveSeuilWinner`/closure are unaffected (still a numeric `value` vs `target_count` compare). `fenetre` ignores color (metric `blocs`) or reuses the classement's own per-boulder `scoreDeltaForValidation` (metric `points`), gated on `now <= ends_at`; `bloc_designe` only reacts to its own exact `boulder_id` and only on success (a fail never lowers a previously-recorded best). None of the three ever re-reads another participant's `progress` entry — each participant's flush only touches its own key, exactly like `colorCounts`.
- **⚠️ Firestore transactions require every `tx.get()` before the first `tx.write()`/`tx.set()`, across the WHOLE transaction, not just per document** — found while building this feature's e2e test (2026-08-19): the pre-existing `wallCounts` write already violated this (`tx.get(userRef)` happened after `tx.set(ref, ...)` for `classement_profiles`), silently swallowed by the transaction's own `catch` block ever since V2.44 (`wallCounts` may have been silently failing to update in prod since then — never visibly broken because nothing surfaces that failure to a user, and no e2e test previously exercised the wall-delta path with assertions on the write's outcome). Fixed alongside this chantier by regrouping every `tx.get()` (classement_profiles, users/wallCounts, every touched challenge doc) before any `tx.set()` in `flushClassementWrite`. Any future addition to that transaction must preserve this "reads, then writes" ordering.
- **⚠️ No write rebuilds a document from in-memory state** (rule proposed by ClaudeNav after the V2.68 missions bug, `docs/handoffs/RETOUR-bug-missions-et-revalidation.md` §4, as a companion to the one above): either the document was read in the same transaction, or the write is additive by construction (`increment`, `arrayUnion`, dotted paths), or it is refused. V2.68 broke it three ways at once: the missions grid rebuilt without reading `user_ludic_state`, and `client_boulder_results` fully rewritten (`setDoc` without merge) from a never-prefilled dialog, wiping rating/comment/proposed grade and replacing `attempts` with the `Select`'s default of 1. The first is fixed in V2.68.1 (see the Weekly missions section). The second and third are fixed in V2.69 (see "Daily boulder results: the first success is the measure" below).
- **⚠️ A test must never create the data whose existence it is testing. If the deliverable is a production document, the check must read it where it lives** (ClaudeNav, `docs/handoffs/RETOUR-v2681-v269-v270.md` §4). This is the third time the project has hit the same shape of failure, where everything looked fine:
  - V2.46: a `catch` swallowed the error.
  - 24/09: React state looked right while Firestore was corrupted.
  - 25/09: the rules test seeded its own `badge-missions`, hiding that the prod catalog never had one.
  - 02/10: the boulder's own result wrote fine, so the climber saw a validated boulder — while the counters transaction was being refused and his score stayed put (`docs/URGENT-flush-bloque-par-challenges.md`). What reassures is once again what misleads.

  **⚠️ A logged error is not a reported error.** If a failure can stay invisible to the user while their data is not being saved, it must surface in the interface, not only in the console (`CLAUDE.md` line asked for by the 02/10 document, §4.19). Corollary learned the same day, and more important than the rule itself — kept verbatim as asked: ***« Une escalade qui ne compte que les échecs consécutifs ne peut pas se déclencher sur un échec sélectif. »*** (An escalation that only counts *consecutive* failures cannot fire on a selective one.) `useDebouncedFlushQueue`'s `onDurableFailure` (threshold 3) had been in place since V2.48 and still showed nothing, because (a) nothing re-tried — a failed payload sat in the queue until the user's *next* action — and (b) any successful validation in between reset the counter. A failure that only hits *some* writes therefore never accumulated three in a row. The hook now re-arms its own timer after a failure (progressive back-off), so the three attempts actually happen and the alert can reach the climber.

  **`scripts/audit-prod-catalog.js`** (read-only, exit code ≠ 0 on error) checks prod against the **contracts** the code assumes. No badge id is hard-coded in the app: attribution is by `type`, walking the catalog. The contracts:
  - at least one `type: 'mission'` badge, with no colour;
  - an `automatic` "réussir un bloc <couleur>" badge for each of violet→rose, since the level sync cannot reach a colour with no badge; plus the "Master";
  - no `client_badges` link to a missing badge;
  - the state of `app_config/classement_saison`.

  Any chantier that depends on a catalog/config doc gets an explicit "create it in prod" deploy step, **verified by running this audit, not by ticking a box**.

  ⚠️ **Une règle d'audit ajoutée à une base qui a un passé doit être précédée d'un rattrapage, ou bornée dans le temps. Sinon elle naît comme un avertissement permanent, et un avertissement permanent n'est plus un signal** (règle proposée par ClaudeNav, `docs/handoffs/RETOUR-auto-inscription-reponses.md` §2, et appliquée le 03/10/2026). Le contrôle « une participation sans `dateOfBirth` alors que son compte en a une » aurait signalé **tout l'héritage** de l'ancienne auto-inscription : né rouge, de façon permanente, sur des cas qu'on ne comptait pas corriger un par un — exactement ce que `KNOWN_EXCEPTIONS` existe pour éviter. L'ordre est donc **rattraper d'abord, contrôler ensuite** : `scripts/backfill-competition-participants.js` a tourné (2 participations, plus la suppression d'un résultat de compétition orphelin), *puis* le contrôle a été ajouté, et il est né vert. À partir de là **toute occurrence est une régression réelle**, et c'est ce qui lui donne sa valeur de signal. ⚠️ Et le rattrapage lui-même a une **fenêtre de tir** : il réécrit des participations, donc modifie rétroactivement les catégories d'âge affichées — gratuit tant qu'aucune compétition réelle n'a eu lieu, réécriture de résultats publiés après la première vraie épreuve. Vérifier cette fenêtre avant, pas après. Enfin, un contrôle né vert sur un terrain propre **ne prouve rien par lui-même** : `frontend/test/backfill-participants-emulator.mjs` l'exerce dans les deux sens, rouge avant le rattrapage, muet après.

  ⚠️ **La distinction qui rend un tel contrôle utilisable est PAR CHAMP, pas par document** : un champ absent de la participation *alors que* le compte le porte est un défaut d'inscription (❌) ; absent des deux est une lacune du **compte** (comptée, tenue hors du rapport). Sans elle, les comptes sans date de naissance repeupleraient le rapport à chaque exécution. Un même document peut porter les deux à la fois.

  **Dead references between collections (02/10/2026, `docs/handoffs/RETOUR-v2714-et-comptes-test.md` §3.2).** The same script now also asks *what points at something that no longer exists?*: `client_boulder_results.boulderId` → `boulders` (the reference the whole classement rests on — this is what makes the "never delete a `boulders` document" invariant checkable instead of merely hoped for), `challenges.participants`/`created_by`/`boulder_id`, and `classement_profiles/{uid}` → `users`. First run, 02/10: **0 dead reference** out of 775 results / 3 challenges / 61 profiles. ⚠️ **One reference cannot be audited server-side, and it was the one that actually broke**: a climber's active challenge is stored *nowhere* — `ClientDaily.tsx` rebuilds it with a cache-first query, so the dead reference lives in the browser's IndexedDB cache. What protects against that is the rule and the transaction split, never this audit. Don't let the audit's green imply that class of defect is covered.

  **Test accounts.** They are for **repeating a destructive gesture** in production before applying it to everyone — the real database, the real rules, the real volumes — never for **detecting** a defect: they are young and clean, and this project's defects grow out of *accumulated state* (a rolling ISO week, a field deleted downstream, a challenge erased months later, a counter inflated by a since-fixed bug). Treating "we checked on the test accounts" as verification would be a fifth member of the "everything looked fine" family above. For detection, the instrument is the production audit, above. Corollary: a test account kept for years becomes *more* valuable, not less — it has crossed every migration (hence keeping "Maurice Tartanpion").
- **Closure is a pull-only action, no cron**: `fenetre` auto-closes itself — any participant who opens `ClientFriends.tsx` after `ends_at` has passed triggers a `useEffect` that computes the winner (`resolveFenetreWinner`) and writes `status: 'termine'`/`winner_uid` right then, first-to-open wins the race (harmless — same result either way). `seuil`/`bloc_designe` show a "Clôturer" button once a winner is computable, clickable by **any** participant (not just the creator — user's call, 2026-08-19); `declaratif` has no computed winner, just a manual "Terminer le défi" button. Firestore rules enforce closure as one-shot and field-scoped: an update may touch `progress` (and only the caller's own key within it, checked via a **nested** `diff()` — `request.resource.data.progress.diff(resource.data.progress).affectedKeys()`, not just the document-level `diff()`) **or** `status`+`winner_uid` transitioning `en_cours` → `termine`, never both in the same write, never re-opening a closed challenge.
- **Deletion (V2.53)**: the creator (`created_by`) may `delete` their own challenge from `ClientFriends.tsx` ("Supprimer ce défi", `window.confirm`), any status — for pulling a test/abandoned challenge. `firestore.rules` `allow delete: if resource.data.created_by == request.auth.uid`. ⚠️ **"Safe mid-flight" was false from V2.53 to 02/10/2026, and it cost real validations.** The claim was that `buildClassementFlushWrites` skips a vanished challenge (`if (!challengeData || !challengeRef) return;`) — true, but **that guard was never reached**: `allow read` evaluated `request.auth.uid in resource.data.participants`, and on a deleted document `resource` is null, so the rule **crashed**, and a rule crash reaches the client as `permission-denied`. The `tx.get()` was refused, the whole shared transaction aborted, and score/wallCounts/missions were lost with it. Worse, `ClientDaily.tsx` loads its challenges **cache-first** (`getDocsCacheFirst`), so a challenge deleted on another device survives in the local IndexedDB cache and poisons every subsequent validation that would advance it — until the cache is cleared (logout does clear it). Fixed on both sides: the rule now short-circuits with `resource == null ||`, and the challenge write left the shared transaction entirely (see the bullet above). Two permanent rules tests lock it (`firestore.rules.test.ts`: reading a nonexistent challenge, and a transaction over a deleted one).
- **No reconciliation script** for `challenges`, unlike `colorCounts`/`wallCounts`'s siblings — same rationale as `wallCounts`: low stakes, short-lived documents, a drift disappears when the challenge ends. Deliberate, not an oversight. ⚠️ **Weaker since 02/10/2026** though (ClaudeNav's reservation, `docs/handoffs/RETOUR-v2714-et-comptes-test.md` §2): `challenges.progress` is now an incremental counter with **both** no safety net **and** a deliberately silent failure path (its transaction's `catch` logs and stops). The two were acceptable separately. Open item, not urgent — nothing is derived from it — but revisit before anything ever reads `challenges.progress` for something that matters.
- Tests: `utils/challenges.test.ts` (pure logic — winner resolution incl. ties, progress deltas incl. removal), `test/firestore.rules.test.ts` (`describe('challenges...')` — create bounds, read/write scoping, closure lock), `test/e2e-challenges-flow.mjs` + `test/seed-challenges-users.mjs` (real browser, `seuil` end-to-end incl. auto-updating from `ClientDaily.tsx`, plus `declaratif`'s manual button) — run manually against local emulators + `vite --port 5174` per the project's existing e2e convention (no npm script wires this in, see Testing section below). **When validating two boulders back-to-back in an e2e script, stay on the same page/mount and wait out the debounce rather than navigating between them** — a `pagehide`-triggered flush is not guaranteed to complete before a real browser navigation tears down the page (no `sendBeacon`/keepalive behind a Firestore transaction), so a hard navigation mid-flush is a flaky way to force a write in a test, even though it's the right mechanism for the app's real "closing the tab" case.


## Weekly missions (`grille de missions hebdomadaires`) — `user_ludic_state/{uid}.weeklyMissions`, V2.68

`docs/plans/PLAN-anecdote-methodes-missions.md` §C: eight missions (M1–M8) reset every ISO week, rewarding a **badge** on first completion (never classement points — seeded from a `reconcile-classement-profiles.js` incompatibility, see below), with a repeat counter (`weeklyMissionsCompleted`) for later completions. Distinct from — and coexists with — `weeklyGoalItems` above: a weekly goal is set *by the climber, for themselves*; a weekly mission is set *by the gym, identical for everyone*, meant to push climbers outside their comfort zone. Don't merge the two, don't remove either.

- **No cron, no server-side date check** — `utils/weeklyMissions.ts`'s `resolveWeeklyMissionsState` compares the stored `isoWeek` (`"YYYY-Www"`, `isoWeekKey()`, standard ISO 8601 Thursday-based algorithm, heavily unit-tested including year-boundary cases) against the current ISO week on the CLIENT's own clock; a mismatch resets `done`/`walls` to empty and **refigures `level`/`countsChildWalls` from whatever is current at that moment** — same trust doctrine as the season window (17/08) and the whole rest of the app's client-clock-driven resets. Never construct a server-side verification for this.
- **`level` and `countsChildWalls` are frozen at week-open, never re-derived mid-week** — both are read once when `resolveWeeklyMissionsState` opens a new week and then simply carried through the object for the rest of that ISO week, exactly like the season restart's `season.baseScore`. `countsChildWalls` comes from `getSeasonAge(dateOfBirth, legacyAge)` — the single point of age derivation, see the `age` vs `dateOfBirth` section above; never recompute age anywhere else for this feature. A climber's 10th birthday mid-week does not change which walls count until the following Monday.
- **The grid is a stamped "bingo card" (V2.70, `Daily/WeeklyMissionsGrid.tsx`, display-only, and `utils/missionGridStyle.ts`, pure)** — `docs/handoffs/RETOUR-bug-missions-et-revalidation.md` §2.11.
  - **Layout**: 8 tiles, 2×4 on mobile and 4×2 from `sm` up.
  - **The stamp**: the gym's mark without typography (`gymConfig.ts` `missionStampMarkUrl` → `src/assets/marque.png`, a white alpha mask with its scratched texture kept on purpose, recoloured via CSS `mask-image`, never vectorised; the "Grimpe !" fork supplies its own there). Ink is `brandGreenDark` on light and `brandGreen` on dark (`brandGreenDark` was nearly invisible on the dark theme, checked on a screenshot).
    - Size: ~75 px when a mission is ticked while the screen is open, then settles at ~26 px in a corner. Never animated on first render.
    - Tilt and opacity are derived from the mission key (`stampAngle`/`stampOpacity`), never random at render.
    - Accessibility: the stamp is `aria-hidden` and done state is also given in text; motion is disabled under `prefers-reduced-motion`.
  - **Colours and pictograms**: M1/M3/M4 carry an accent band in the relevant level colour (`missionAccentLevel`: frozen level / max−1 / max+1, none for M4 bis), with an outline for pale colours on light and for `noir` on dark. M5/M6/M7 get pictograms. M2 shows 4 segments.
  - **Header**: frozen-level chip, "N / 8", and a greyed badge that lights up at completion.
  - **Test hook**: `data-mission-done` on each tile is what `e2e-weekly-missions-flow.mjs` counts.
  - **Stamp reuse, V2.70.1**: ClaudeNav's condition (don't reuse the stamp until it has been seen for real on the grid) was met on 25/09/2026. The user then chose the stamp to replace the medal on the mission badge card in "Mes stats": white stamp on a `brandGreen` header, via `components/GymStampMark.tsx`, the static counterpart of the grid's stamp. The badge's colour comes from its **type**, never from its `color` field. `badgeDisplayColor`/`isMissionBadge` in `utils/badgeActivation.ts` handle it, and the home "Dernier badge obtenu" chip uses the same helpers. Setting a `color` on the badge doc, even a hex, would make `computeBadgeActive` look for boulders of that "colour" and put the badge to sleep. The prod catalog doc is `badges/badge-missions`: "Badge du grimpeur régulier" / "Badge de la grimpeuse régulière", created by hand on 25/09/2026 because no deploy step had ever created it (see `docs/handoffs/HANDOFF-bug-missions-revalidation-bingo-2026-09-25.md` §4 bis). Still not reused for roulette.
  - **V2.70.2**: the mission badge card shows `weeklyMissionsCompleted` ("N semaines complètes"). One badge, with repetition carried by the counter. Until the badge is owned, `ClientStats.tsx` shows it as a greyed stamp silhouette ("Pas encore obtenu"). The grid header's badge icon is now that same stamp (`GymStampMark`), no longer a medal, so both screens tell the same story.
- **M1 on an already-validated boulder goes through the "Je l'ai refait" gesture (V2.69), never through "Réussi".** V2.68 evaluated missions on the "Réussi" click before the dedup guard, so re-clicking "Réussi" on an old boulder ticked M1. But that same click also **rewrote the original result** (`setDoc` without merge from a never-prefilled dialog: attempts replaced by the Select's default of 1, rating/comment/proposed grade wiped). Since V2.69 an already-succeeded boulder's dialog is read-only, and M1 is reached by the mission gesture instead (see the re-validation rule section below). It stays declarative (trust gap accepted, same doctrine as the season score and Roulette). ⚠️ **If weekly missions ever award classement points, the gestures must not count** — the trust gap is fine for a badge, not for points.
- **M3 (flash) requires a boulder never tried before (V2.69)**: `BoulderValidationEvent.neverTriedBefore` must be `true`, meaning no stored `client_boulder_results` for that boulder (neither success nor failure) **and** `attempts === 1`. A one-attempt repeat is not a flash (motor memory, `docs/handoffs/RETOUR-bug-missions-et-revalidation.md` §2.6). Only the caller knows whether a stored result exists, so it passes the flag; the gestures always pass `false`.
- **M4 bis substitutes M4 for a climber at the level ceiling (rose)**, rather than leaving that cell permanently unreachable. M3's floor and M4's ceiling clamp reuse the Roulette's own `resolveTargetColor`/`levelOrder` (`utils/roulette.ts`) — do not write a second clamp implementation. `isAtLevelCeiling()` in `utils/weeklyMissions.ts` is the one place that decides which of M4 or M4-bis applies; the grid always shows exactly 8 cells regardless. M4-bis is **purely declarative** ("Réussir un bloc de ton niveau max en t'interdisant une prise de main ou de pied", a `MISSION_M4_BIS_LABEL` constant), reusing the Roulette's "J'ai relevé le défi" pattern — no boulder validation backs it. In prod, at the time this shipped, only one account (the ouvreur) is permanently at the ceiling, so this path is exercised rarely by construction, not because it's unimportant.
- **⚠️ V2.68 shipped a grid-erasing bug, fixed in V2.68.1** (`docs/handoffs/RETOUR-bug-missions-et-revalidation.md`, reproduced by `test/e2e-weekly-missions-flow.mjs` before the fix): the flush only added `user_ludic_state` to its transaction reads `if (pending.wallDeltas.size > 0)` — a condition written before missions existed. `wallDeltas` is only non-empty on a *first* success, so any flush carrying only missions (a failure → M4/M2, a re-validation → M1) rebuilt `weeklyMissions` from an empty grid and overwrote the stored one (`done`/`walls` are arrays: `merge:true` replaces them). M4 is *nominally* earned by a failure, so every climber doing M4 wiped their grid. Fix: the read set is now derived by the pure `classementFlushReadKeys(pending)`, `ClassementFlushReadData.readKeys` distinguishes "not read" from "document absent", and `buildClassementFlushWrites` **throws** on any write to a document it didn't read (a lost-but-loud write beats silent corruption — the queue retries then alerts). `classementFlushWrites.test.ts` checks this as a **property** over all 1024 presence/absence combinations of `pending`'s fields: adding a field to the shared transaction without extending the read keys fails the test by itself.
- **M8 folds into the Roulette's existing write, M1–M7 fold into the shared debounced classement-flush transaction — never a standalone write.** `services/ludicState.ts`'s `incrementRouletteCompleted` now also resolves/advances `weeklyMissions` as part of the SAME write it already made for the roulette counter. **Since V2.68.1 that write (and M4 bis's, `recordDeclarativeMission`) is a `runReadThenWriteTransaction` that re-reads `user_ludic_state`**, with the patch computed by the pure `utils/ludicStateWrites.ts` — before, both recomposed `weeklyMissions`/`rouletteRecentChallenges` from the React state loaded at mount (lost update as soon as the flush or another tab wrote in between). `arrayUnion` was considered (ClaudeNav §1.4) and not used: the weekly reset needs `isoWeek` read anyway, and `weeklyMissionsCompleted`/`completedAt` depend on the actual `done` content. The screen then merges the written grid with its in-memory one (`mergeWeeklyMissionsForDisplay`, same-week union) since memory can hold missions whose debounced flush hasn't gone out yet. For M1–M7, `ClassementFlushPending` (`utils/classementFlushWrites.ts`) gained `missionsNewlyDone`/`wallsNewlyVisited` (Set-based, unioned across merges — commutative like the rest of that file) plus a `missionsFige` snapshot (level/countsChildWalls, constant for the session); `buildClassementFlushWrites` combines any resulting `weeklyMissions` patch with the pre-existing `wallCounts` patch into a **single** write to `user_ludic_state` — never two separate `tx.set()` calls to the same document reference in one transaction. **M4-bis is the one exception**, with its own small dedicated write (`recordDeclarativeMission` from `handleMissionM4Bis`, transactional since V2.68.1) — there's no other write already happening at that exact moment to piggyback on, and the interaction is rare enough (see above) that the extra write is immaterial to the chantier's near-zero net read/write cost.
- **Badge is `type: 'mission'`, a THIRD badge type alongside `manual` and `automatic` — never reuse `automatic`.** `computeBadgeActive()` (`utils/badgeActivation.ts`) treats a badge with no `criteria.color` as "always active" — exactly what a mission badge is, so running it through the existing `automatic`-badge auto-attribution loop in `ClientStats.tsx` would have awarded it to every account on their very first "Mes stats" open. Fixed by branching: `type: 'automatic'` still goes through `computeBadgeActive`, `type: 'mission'` is active whenever `weeklyMissionsCompleted >= 1` (already fetched via `getLudicState` in the same function, zero extra reads) — evaluated once, awarded once (`client_badges/{uid}_{badgeId}`, `awardedBy: 'auto'`, deterministic id, same immutability as every other auto-attributed badge). `firestore.rules`' auto-attribution `create` rule widened from `type == "automatic"` to `type in ["automatic", "mission"]`.
- **A fourth idea from the same planning document — a "mode flash" (double points for 30 minutes) — was explicitly rejected**, not deferred: `reconcile-classement-profiles.js` recomputes the expected score from validations and each boulder's color, so it would silently erase any points from another origin on its next monthly `--fix` pass, and the app has no push-notification infrastructure to announce a flash window to anyone not already looking at their phone. Don't reintroduce it without solving both problems first.


## Weekly goals (`ClientScreen.tsx`) — cumulable since V2.52, computed live, never persisted as a counter

`users/{uid}.weeklyGoalItems: WeeklyGoalItem[]` (introduced V2.52, `utils/weeklyGoal.ts`) replaces the earlier single `weeklyGoalTarget: number` ("N blocs, tous niveaux confondus") with a **cumulable list** of goals for the current week (Monday to today): `{type:'color', color, target}` (e.g. "2 rouges"), `{type:'boulder', boulderId, boulderLabel}` (a specific boulder, e.g. "bloc n°6 - Dalle"), or `{type:'all', target}` (the old behavior, kept as one selectable goal type among others, not removed). Items are freely combinable in one list (e.g. 2 rouges + 3 noirs + one specific boulder), capped at `MAX_WEEKLY_GOAL_ITEMS` (8).

- **`utils/weeklyGoal.ts` is a pure module, no Firestore import** — same discipline as `roulette.ts`/`challenges.ts`. `computeWeeklyGoalProgress(items, validationsThisWeek, colorById)` returns per-item `{current, target, done}`; `upsertGoalItem` replaces (never duplicates) an existing item of the same kind (same color, same boulderId, or the single `'all'` item) when the user adds another one like it — avoids the ambiguity of two "rouge" goals in the same list. Unit-tested in isolation (`weeklyGoal.test.ts`), no emulator needed.
- **Progress is recomputed live on every page load, exactly like the pre-V2.52 design — deliberately not an incremental counter** (unlike `classement_profiles`/`wallCounts`/`challenges.progress`): `ClientScreen.tsx` already read all of the user's own `client_boulder_results` (success:true) once per mount for the streak feature: the same read now also carries `boulderId`, filtered to this week, and is joined against a lazily-loaded `colorById` map (`boulders` where `type=='daily' && is_active==true`, fetched only when at least one `'color'`-type goal exists — a `'boulder'`/`'all'`-only goal list costs zero extra reads). This is a personal, low-stakes, cheap-to-recompute stat — same rationale as `wallCounts` having no reconciliation script.
- **Same "createdAt this week" semantics for all three goal types, including `'boulder'`, by deliberate choice**: `client_boulder_results.createdAt` is immutable after first success (see below); a goal is "done" when a boulder's (or a color's) **first-ever** success falls within the current week's window, not merely re-validated this week. For a `'boulder'` goal this means picking an already-long-validated boulder as this week's goal is honestly shown as not-done-this-week rather than trivially satisfied — consistent with `'color'`/`'all'`, not a special case.
- **Legacy read-time fallback, same pattern as `legacyAge`/`image_base64`**: `legacyGoalToItems(weeklyGoalTarget)` converts an old-shaped `weeklyGoalTarget` number into a single-item `[{type:'all', target}]` at read time for accounts that set a goal before V2.52 — `weeklyGoalTarget` is never written again; the first time a user saves from the new dialog, it's cleared via `deleteField()` and `weeklyGoalItems` takes over as the only field going forward.
- **`'boulder'` goal picker reuses the "bloc désigné" challenge pattern verbatim** (`ClientFriends.tsx`'s `bloc_designe` structure): same lazy query (`boulders`, `type=='daily'`, `is_active==true`), same composed label `` `${color} n°${number} - ${wall}` ``. No new UI convention introduced.
- No Firestore rules change was needed — `weeklyGoalItems` is just another field on the user's own `users` doc, already covered by the existing permissive `update` rule (the only locked keys are `inscritAuxCours`/`inscritAuxCompetitions`/`role`/`roles`/`levelOverride`).
- Not included in the "Partager ma progression" share card — unchanged from before V2.52, that card only ever surfaced level/badge/streak.
