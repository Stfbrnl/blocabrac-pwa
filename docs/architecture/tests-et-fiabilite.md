## Swallowed-error process (`docs/processus/PROCESSUS-erreurs-avalees.md`, V2.47 → V2.49, now complete)

Written by ClaudeNav straight after the V2.46 transaction bug above — not about that one bug (already fixed) but the *class* of bug it represents: a permanent, deterministic failure disguised as a retryable transient one, silently swallowed by a `catch` that just re-queues and never surfaces. Four steps; §1/§2/§4 landed in V2.47, §3 (the structural refactor) in V2.48 as its own dedicated version, per the document's explicit warning not to mix it with the others — it touches three production write paths that had each already been the site of a real data-loss fix once before.

- **§1 (inventory via ESLint, report mode)**: `eslint.config.js` sets `@typescript-eslint/no-unused-vars` with `caughtErrors: 'all'` and `no-empty` with `allowEmptyCatch: false`, both at `'warn'` (not `'error'`) — deliberately non-blocking until the existing surface is fully triaged. **Result: zero findings** — every `catch` in the codebase already reads its error variable in some form, so this heuristic didn't catch the V2.46 bug and wouldn't have; it exists for the empty/no-op case, not the "logged once, retried forever" case that actually happened. Still `'warn'`, not flipped to `'error'` — that flip is its own separate, still-open step (§6 of the document), not bundled into §3.
- **§2 niveau 1 (console.error everywhere)**: audited every debounced-flush write path — `console.error` added to `ClientCompetitions.tsx`/`ClientCourseSession.tsx`'s catches (they already had user-facing `setError`, just missing the console trace for the screenshot-diagnosis case CLAUDE.md's own testing conventions rely on).
- **§4 (assert the effect, not just "didn't crash")**: `e2e-daily-flow.mjs` gained a direct backend assertion (`firebase-admin`, bypassing rules) on `users.wallCounts` after a validation — the exact counter the V2.46 bug had silently broken, and the concrete reason this e2e never caught it: it asserted the classement was right but never checked `wallCounts` at all. `season.*`/`classement_profiles` were already asserted this way in `e2e-season-classement-flow.mjs`. `challenges.progress` remains covered for `seuil`/`declaratif` only, not `fenetre`/`bloc_designe` — pre-existing gap, unchanged, see `docs/handoffs/HANDOFF-defis-entre-potes-2026-08-19.md`.
- **§3, part A — the transaction helper (`utils/firestoreTransaction.ts`)**: `runReadThenWriteTransaction(db, reads, buildWrites)` takes a flat `Record<string, DocumentReference>` of everything to read and a **pure** `buildWrites(readData) => TransactionWrite[]` function — `buildWrites` never receives `tx` itself, so it is *structurally* impossible for it to call `tx.get()` after a write; the helper does every read (in key order) before calling `buildWrites` and applying its writes. `ClientDaily.tsx`'s `flushClassementWrite` is the only caller today (`classement_profiles`/`users.wallCounts`/`challenges.progress`, the exact transaction that had the V2.46 bug) — its write-building logic was extracted into `utils/classementFlushWrites.ts`'s `buildClassementFlushWrites`, now a plain function with **no Firestore import**, unit-tested (`classementFlushWrites.test.ts`, 12 cases) without an emulator — the "bénéfice secondaire" the document predicted.
- **§3, part B — one debounced-flush hook (`utils/useDebouncedFlushQueue.ts`)**: replaces three separate hand-rolled implementations (`ClientDaily.tsx`, `ClientCompetitions.tsx`, `ClientCourseSession.tsx` — the document counted the défis path as a fourth, but its writes already shared `ClientDaily`'s single transaction, so there were only three distinct implementations, not four) that each had their own timer bookkeeping, their own technique against a stale `pagehide` closure (a ref-of-closure here, a `useCallback` dependency list there, a dependency-less effect elsewhere — now just one), and their own ad hoc catch. The hook is generic over a per-key payload `T` and a caller-supplied `merge(older, newer) => T`: **accumulate** semantics (`ClientDaily`'s classement delta — `mergeClassementFlushPending`, additive) and **replace** semantics (`ClientCompetitions`/`ClientCourseSession`'s per-boulder/per-exercise validation snapshot — `(_older, newer) => newer`) both fit the same contract; the hook always **re-queues on failure** using that same `merge`, a small robustness upgrade for the two "replace" screens (they used to silently drop a failed write with no retry at all). Console logging, the failure counter (§2 niveau 2), and escalation to a caller-supplied `onDurableFailure`/`onRecovered` (§2 niveau 3, reusing each screen's existing `error`/`Alert` state, never a new `Snackbar`) are now inside the hook, not copy-pasted per screen. `ClientCompetitions`/`ClientCourseSession` keep `failureThreshold: 1` (they already surfaced every failure immediately, stronger than `ClientDaily`'s tolerance for a transient blip, commented at each call site so nobody "helpfully" aligns them later) plus a new `onRecovered` clearing the error on the next success.
  - ⚠️ **The `merge` contract's argument order is `(older, newer)`, never `(prev, incoming)`** — found by ClaudeNav's review the same day this shipped (V2.50). The hook calls `merge` from two places with an *opposite* freshness relationship: in `enqueue()`, what's already queued is older than the arriving payload; in the failure-retry path, the payload that just failed is older than whatever got enqueued during the failed `await`. A naive `merge(prev, incoming)` that special-cased "prev wins if it exists" (right for the retry case) was silently *wrong* for the enqueue case — two rapid edits within one debounce window (e.g. essais 2 then 3) would persist the **first** value, not the last, because "prev" in that call is the older one. The additive case never exposed this (addition is commutative, order doesn't matter — which is exactly why it shipped unnoticed). Fixed by making the hook itself respect strict age ordering at both call sites and only ever handing `merge` two arguments it's already labeled `(older, newer)`; the undefined-on-one-side cases (nothing queued yet / nothing newer since the failure) are handled by a separate pure `combineByFreshness` helper before `merge` is even called, so `merge` itself only ever sees two real values. `combineByFreshness` is exported and unit-tested (`useDebouncedFlushQueue.test.ts`) — including the exact "essais 2 then 3" scenario — the one piece of this hook that *can* be verified without a React test harness, and the one that actually would have caught this.
- **Verification for §3**: the existing e2e suite was the filet, exactly as the document asked — `e2e-daily-flow.mjs` (wallCounts assertion), `e2e-challenges-flow.mjs`, `e2e-season-classement-flow.mjs` (all three exercising `ClientDaily`'s migrated transaction), `e2e-competition-flow.mjs` (`ClientCompetitions`), `e2e-course-flow.mjs` (`ClientCourseSession`'s exercise queue). 59 e2e steps green, no regression, alongside the full `npm test`/`npm run test:rules` suite.
- **§1/§6 closed in V2.49**: `e2e-course-minicompetition-flow.mjs` + `seed-course-minicompetition.mjs` close the one flagged gap — `ClientCourseSession.tsx`'s *other* queue (`boulderQueue`, mini-compétition results, distinct from the exercise queue `e2e-course-flow.mjs` already covered) now has its own dedicated 10-step e2e (immediate write on "Réussi", debounced `enqueue` on the essais `Select`, a direct `firebase-admin` assertion on the written `client_course_results` doc, survival across a reload, the final "Enregistrer" `writeNow`, and the archived read-only view). Same run also flipped `eslint.config.js`'s `@typescript-eslint/no-unused-vars`/`no-empty` from `'warn'` to `'error'` — the inventory was still zero, so this was a pure formality, not a fix.


## Form labels and accessibility: `aria-labelledby`, never `htmlFor` on a MUI `Select` (03/10/2026)

`docs/plans/PLAN-labels-non-associes.md` and its three retours (`RETOUR-labels-non-associes.md`, `RETOUR-labels-dom-lu.md`, `RETOUR-labels-apres-dom.md`). The chantier started from Chrome's Issues panel reporting "No label associated with a form field" on the Ouvreur daily-boulders screen, and ended by establishing that **73 of the 77 `InputLabel` in the repo were already correct**.

- **The canonical wiring for a manually-composed field is `InputLabel id` + `Select labelId` + `Select label`** — three properties, and **never a fourth `htmlFor`**. A `Select` renders a `div role="combobox"` plus an `aria-hidden` native `<input>`; the `id` prop lands on **the div**, which is not a labelable element (read in the rendered DOM with Playwright, not in the docs — `MuiSelect-select` carries `id`, the native input gets an auto-generated `:r1b:`). A `for` pointing at it resolves to no form field (`label.control === null`), and Chrome simply swaps "No label associated" for "The label's for attribute doesn't match any element id". A combobox is named by `aria-labelledby`, which `labelId` already sets correctly. `TextField` is exempt from all of this — MUI generates both the `id` and the `htmlFor` and points them at the real field, which is why a `TextField` is never flagged.
- ⚠️ **Inside a render loop, derive the `id` from the data, never freeze it** (`ClientCourseSession.tsx`, the attempts `Select` rendered once per exercise and once per mini-competition boulder). A frozen literal produces N duplicate ids, and `aria-labelledby` then resolves to the first one for every row — one defect traded for another, and **invisible to both of Chrome's warnings**.
- **Two deviations are accepted, documented, and not fixable from this repo** — same doctrine as `audit-prod-catalog.js`'s `KNOWN_EXCEPTIONS`, because a permanent warning teaches people to ignore warnings:
  1. **"No label associated with a form field"** on every manually-composed `Select` — Chrome's heuristic only looks for `label[for]` → form field and cannot read `aria-labelledby`. The repo follows MUI's own recommended pattern, and it is correct for a screen reader.
  2. **"A form field element should have an id or name attribute"**, twice per multiline `TextField` — `TextareaAutosize`'s hidden measuring textarea (`aria-hidden`, `readOnly`, `tabIndex: -1`), rendered by MUI with no prop to reach it. In `@mui/material` v9.1.1, `multiline` implies `TextareaAutosize` **unconditionally** (`InputBase.js` 449-467 maps `rows` to `minRows`/`maxRows`), so there is no multiline field without a phantom. 17 in the repo.
- 🔴 **Therefore "zero Chrome warnings" is never a valid exit criterion for this area** — it is unreachable on *both* warning types. The criterion is the net below. Chrome also flags fewer fields than exist: the daily-boulders screen has 4 fields with neither `id` nor `name` (2 phantom textareas, the "Bloc enfant" checkbox, the file input) for only 2 warnings — it ignores fields that aren't autofillable, so adding an `id` to the `<input type="file">` silences nothing.
- **The net is `frontend/test/assertNoOrphanLabels.mjs`**, called from an e2e on each visited screen (wired into `e2e-daily-flow.mjs` for 5 screens and `e2e-course-minicompetition-flow.mjs` for the looped case; **reproduce it in the others**). It checks the rendered DOM, where MUI's markup actually exists, and verifies three things: ① every label has a `for` resolving to a labelable element, **or** an `id` referenced by some `aria-labelledby`, **or** its field nested inside it; ② every field has an `id` or a `name`; ③ no duplicate id among labels and fields. ⚠️ **`aria-hidden` is excluded from ② only, never from ① or ③** — the phantom textarea must not be required to have an id, but a `Select`'s own native input *is* `aria-hidden` and remains a valid label target; excluding it everywhere would turn the net red *because of* a correct fix. All three were seen red before being green, and ③ had no subject until `seed-course-minicompetition.mjs` was given a **second** boulder — with one, a frozen loop id produces no duplicate and the net stays green without checking anything.
- **Abandoned deliberately**: `htmlFor` on the 77 (wrong, see above); `eslint-plugin-jsx-a11y`'s `label-has-associated-control` (the repo has **0** raw `<label>`, so a JSX-literal rule sees nothing without a `components` option); and `§3.4` of the plan (a hardcoded white background behind a label — it never existed; the white in the DevTools Styles pane came from **ancestor** rules, `Paper` then `body`, listed with their non-inherited properties struck through. Three concordant readings. A styles excerpt copied out of the inspector **loses the strikethrough**, hence loses the information about what actually applies — ask which lines are struck through before reasoning on one.)


## A redirect target must be a terminal page, never a route that redirects in turn (03/10/2026)

`RETOUR-labels-apres-dom.md` §3. `ProtectedRoute` used to answer a missing role with `<Navigate to="/" replace />`. But `/` is `Home`, whose `useEffect` pushes to `/client/screen`, itself guarded by `role="client"` — so an account whose `roles` lacks `client` spun in an **infinite redirect loop**: flickering screen, then Chrome's "Throttling navigation to prevent the browser from hanging", and the app **totally unusable**, not degraded. Measured: **77 navigations** against ~5 on the nominal path.

Production was protected only by the convention that every account carries `client` (`AdminUsers.tsx` + `hasClientRole()` in rules) — a convention, not a constraint: un-ticking `client` on an ouvreur account from the admin screen was enough to lock that person out, with no recourse but a direct edit in the Firebase console. And the next planned chantier ("droits d'accès, rôle ouvreur trop large") is the one that touches roles.

- **Fixed by terminality, not by `replace`**: `components/AccessDenied.tsx` is rendered in place by `ProtectedRoute` and navigates nowhere. `replace` instead of `push` would not have helped — the ping-pong between the two routes would remain. Terminality removes the whole class, for any present or future combination of roles.
- ⚠️ **The invariant has a second half, added 03/10/2026 on review: a terminal page must ALWAYS OFFER AN EXIT, and that exit must not itself be a redirect.** Otherwise an infinite loop has merely been traded for a dead end — better, but not enough. The first version of this screen offered only a "Retour à l'accueil" link, which for a `client`-less account **leads straight back here** (Home pushes to /client/screen, which re-renders it): one hop per click rather than a loop, but the exit door reopens on the same room. The screen therefore also carries a **logout** button, which is the exit that works for any combination of roles. `e2e-access-denied-flow.mjs` requires it and was seen red without it ("aucun bouton de déconnexion : l'écran terminal est un cul-de-sac"). The Navbar, rendered in `main.tsx` **outside** `AppRoutes`, is present on this screen too and offers logout gated on `user` alone — but a terminal page must not depend on its surroundings for having an exit.
- **`Home` still assumes `client`** — settled, closed: routing it by role costs a Firestore read on every app open, for everyone, and once the screen above exists it buys no correctness, only a slightly more direct landing for accounts the invariant says don't exist. Measured rather than argued (`getDoc` instrumented in a driven browser): the roles are **not** in a context, they're local state in `ProtectedRoute`, and `Home` renders *before* any protected route, so it really is +1 read.
- 🟠 **But the measurement found something else, and it is the open item: `Navbar` and `ProtectedRoute` each read `users/{uid}` on their own — two reads of the same document per page load, and more importantly two components deciding independently what a user's roles are.** That divergence-in-waiting is what the redirect loop was a symptom of: the knowledge about roles is scattered, `Home` has none, `ProtectedRoute` keeps its own, `Navbar` re-reads it. The fix is a shared context, so that **only one place answers "who is this user"**.
  - ⚠️ **Never justify that chantier by the read saving.** Going from 2 reads to 1 at 61 accounts is the same order of magnitude as `AdminUsers`' 8.4 % (see the ludic-state measurement above): negligible, and a quantitative justification that collapses on measurement discredits an otherwise correct chantier. Argue it on the single source of truth, never on the quota.
  - **When to do it: with the "droits d'accès, rôle ouvreur trop large" chantier**, pending the gym manager. That one touches roles precisely, so unifying their source then costs almost nothing beyond the chantier itself; doing it now means opening the auth plumbing for no reason. Status: *not now*, not *abandoned*.
- ⚠️ **`seed-daily-users.mjs` keeps its ouvreur with `roles: ['ouvreur']`, without `client`, on purpose — do not "fix" it.** That violation is the only thing that has ever exercised this path; adding `client` would have deleted the evidence rather than the defect (the project's recurring failure mode: silencing the signal instead of treating what it pointed at). `test/e2e-access-denied-flow.mjs` turns it into a standing test case.


## Testing

- `npm test` (fast, no external deps) covers pure utility functions (`utils/*.test.ts`) — this is what CI-equivalent checks should always run.
- `npm run test:rules` (Firestore emulator, `frontend/test/*.test.ts`) is the only way to verify Firestore security rules and cross-collection permission logic (e.g. `canValidateCourse`, role checks). Any change touching `firestore.rules` or a write path's field shape should get a test here, following the existing pattern: `initializeTestEnvironment` + `withSecurityRulesDisabled` to seed fixtures, then `assertSucceeds`/`assertFails` against role-specific `authenticatedContext`s.
- There is no Playwright/browser E2E suite wired into these npm scripts, despite `playwright` being a devDependency — manual/agent-driven browser testing is done ad hoc, not via a committed test suite.
- ⚠️ **Launching the e2e dev server on Windows: quote the assignment.** `cmd /c set VITE_USE_EMULATOR=true && npx vite` gives the variable the value `"true "` — trailing space — so `=== 'true'` is false and **the app connects to PRODUCTION instead of the emulator**. The only symptom is the e2e failing at its login step with a bare `403`. Write `set "VITE_USE_EMULATOR=true"`. Found 02/10/2026. Each e2e flow also has its own `seed-*.mjs` (`seed-daily-users`, `seed-weekly-missions-users`, …) — chaining two flows without `emulator-reset.mjs` plus the right seed gives 0/N from the login step on.
- **e2e isolation**: `test/emulator-reset.mjs` (`resetEmulators()`) wipes the local Firestore and Auth emulators through their `localhost`-only `/emulator/v1/...` REST API. The season seeds (`seed-season-classement-users.mjs`, `seed-season-restart-users.mjs`) call it first.
  - `resetEmulators()` **throws** unless both `FIRESTORE_EMULATOR_HOST` and `FIREBASE_AUTH_EMULATOR_HOST` point to localhost. It is an explicit guard, not just a property of the protocol.
- **Known exceptions in `audit-prod-catalog.js`**: accepted deviations live in its `KNOWN_EXCEPTIONS` map, each with a reason and the date the user decided. The audit prints them on an `ℹ️` line, not as warnings, so a *new* warning stands out. A permanent warning teaches people to ignore warnings. Only add an entry on the user's explicit decision.
  - Current entry: the May 2026 legacy `client_badges` doc on the test account "Maurice Tartanpion".
  - The user keeps several test accounts on purpose. The manual moniteur badges (débutant / intermédiaire / avancé / expert) are the original course-progression system and must stay.
  - Why: `e2e-season-restart-flow.mjs` failed its step 8 when run right after the classement e2e on the same emulator, because of drift on the previous test's leftover client. That is a red that looks like a regression and trains people to ignore reds. Verified: both suites run back-to-back twice, all green.
  - Any new seed whose e2e asserts global state (reconciliation over *all* profiles, counts) should call it too.

#### Two method rules from 03/10/2026, both learned the hard way

- ⚠️ **An exit criterion must predict *every* observable counter, including the ones expected not to move.** Asked to verify a one-field fix, the criterion was "the « No label associated » count must go from 4 to 3". **It did — and the fix was wrong.** Chrome had merely *reclassified* the same label into a third warning nobody had been told to look at ("the label's for attribute doesn't match any element id"). Had the user reported only the agreed number, a wrong pattern would have been applied to 77 places. This is the companion to the 02/10 rule (*write the expected delta down first, then attribute it*) for the case where several quantities move at once: **one counter moving the hoped-for way measures the hope.**
- ⚠️ **Hierarchy of evidence, as this chantier actually ranked it**: ① **the rendered DOM** settled it (Playwright, `page.evaluate`); ② **the library's installed source misled** — the right file and the right line, but the wrong variable (`other.id` is empty, `buttonId` carries the caller's `id`), and the conclusion was then written up as "ruled out on the evidence", which lent a reading the authority of a measurement; ③ the documentation was never consulted and was never needed; ④ **a counter moving the right way nearly validated a false pattern**. Reading the source is not reading the DOM. For anything about generated markup, drive a browser.
- **Corollary on home-made instruments** (same day, three times): an inventory script reported 59 `Select` without a `label` prop — it cut the opening tag at the first `>`, which falls inside an `onChange`'s `=>`; the real count was **0**. A network reading of 0.2 Ko was an artifact of clearing the DevTools log, which deletes the very long-lived WebChannel row Firestore's documents arrive on. Both wrong numbers were **the right order of magnitude and consistent with expectation**, hence invisible. What caught both: **a hand-check of one case picked at random from the list.** An automated inventory measures its own defects silently, and all the more so when it was written for the occasion.

#### ⚠️ « Voir rouge d'abord » a une condition que personne n'avait énoncée : le jeu de données doit pouvoir produire le défaut

Le piège le plus retors des deux jours, et il est **à l'intérieur du garde-fou** (03/10/2026, formulé par ClaudeNav après l'avoir rencontré deux fois dans la même journée).

Pour vérifier qu'un filet attrape, on remet le défaut et on s'attend au rouge. Deux fois le même jour, **la tentative de voir rouge a produit du vert** — et on en aurait conclu que le filet fonctionnait :

- `seed-course-minicompetition.mjs` ne créait **qu'un** bloc : en figeant l'identifiant du `Select` rendu dans la boucle, aucun doublon n'apparaissait.
- `e2e-competition-flow.mjs` ne créait **qu'un** bloc de compétition : en restaurant les trois identifiants figés qui étaient en production, le filet est resté vert.

Dans les deux cas le filet était bien « vu attraper quelque chose » — par ses *autres* vérifications, ce qui masquait que celle-là ne vérifiait rien. Corrigé en donnant un second élément à chaque jeu d'essai, commenté sur place pour que personne ne le « simplifie ».

> **La question à poser à chaque seed : quels défauts ce jeu de données est-il physiquement incapable d'exprimer ?**

Elle dépasse largement les libellés : **un jeu d'essai à un seul élément ne peut exhiber aucun défaut de multiplicité, d'ordre, de collision ou de concurrence.** À appliquer à tout nouveau `seed-*.mjs`, et à relire avant de conclure d'un rouge obtenu — ou pas obtenu.

⚠️ **Et la règle ne s'arrête pas au seed : elle vaut pour tout ce que l'assertion REGARDE** (03/10/2026, troisième rencontre, sur `e2e-live-display-flow.mjs`). Un pas censé vérifier que des grimpeurs à égalité partagent le rang 1 lisait « la page courante » de l'écran live — dont la rotation tourne pendant le test. Il est tombé sur une page de catégorie à **une seule ligne**, où « tous les rangs valent 1 » est vrai **sans rien prouver** : vert, et vide. Le seed, lui, était irréprochable (dix participants). Donc : *de quoi la fenêtre d'observation est-elle faite au moment où j'affirme ?* Un pas qui lit un écran qui tourne, pagine, ou se rafraîchit doit **désigner** ce qu'il lit (ici : attendre explicitement la page « Top 10 » et exiger au moins deux lignes), jamais prendre ce qui passe. Même famille que les trois instruments maison faux de la veille : la mesure était du bon ordre de grandeur, donc invisible.

⚠️ **Technique mécanique qui remplace cette vigilance : avant d'affirmer quelque chose sur un ensemble, affirmer sa taille** (proposée par ClaudeNav, `docs/handoffs/RETOUR-auto-inscription-reponses.md` §5, parce qu'une question de jugement à poser à chaque assertion ne tient pas dans la durée). Le pas sur les rangs partagés devait exiger « cette page compte au moins 2 lignes » avant « tous les rangs valent 1 » ; le pas sur le libellé du bouton devait exiger « au moins un autre grimpeur est inscrit » avant d'affirmer quoi que ce soit. Une ligne par assertion, et la question de jugement devient une vérification automatique. À appliquer à **tout sujet sélectionné dynamiquement** : une page courante, un premier élément correspondant, un affichage en rotation.

⚠️ **Un repli rend aveugle au défaut qu'il compense : la défense en profondeur et l'observabilité sont en tension.** Trouvé le 03/10/2026 en cassant quatre correctifs un par un (`RETOUR-auto-inscription.md` §4) : une fois l'écran live doté d'un repli sur `users`, casser l'écriture de l'identité ne le fait plus rougir — il range correctement le grimpeur malgré une participation vide. Le repli fonctionne exactement comme voulu, **et** il a retiré sa force au seul test qui regardait l'écran. **Donc : quand on ajoute un repli, on ajoute ou on vérifie dans le même geste l'assertion sur ce dont on se replie — ce qui est ÉCRIT, pas ce qui est AFFICHÉ.** Sinon on vient de désarmer silencieusement un test existant.

⚠️ **Corollaire sur les filets à plusieurs propriétés : vérifier que chacune rougit SÉPARÉMENT.** Sur ce même écran, deux pas gardent deux propriétés (les rangs d'une tranche valent les rangs globaux ; des grimpeurs à égalité partagent leur rang). En remettant `index + 1`, **un seul des deux rougit** — le tirage n'a aucune égalité dans le top 10. Un filet « vu attraper quelque chose » ne dit rien de celles de ses vérifications qui ne vérifient rien ; c'est exactement ce qui avait masqué le défaut des libellés en boucle. Casser le code **une fois par propriété**, pas une fois pour le filet.
