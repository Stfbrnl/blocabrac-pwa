## 3. V2.56 — Redémarrage du classement de saison

**Origine** : le classement de saison a démarré avec la diffusion publique, faussé
tant que peu de grimpeurs sont équipés. L'utilisateur veut le redémarrer
(mi-septembre) **sans faire revalider les blocs**.

**Modèle A** (confirmé par l'utilisateur après clarification) : au redémarrage,
`season.*` de chacun est **recalculé** depuis ses validations existantes des blocs
encore posés (essais d'origine conservés) et figé comme **crédit de départ**
(`season.baseScore` / `season.baseColorCounts`) ; ensuite `season.*` **s'accumule
et ne redescend jamais** quand un mur change.

**Ta 3ᵉ voie retenue** (`RETOUR-redemarrage-saison-modele-a.md` §1) — plutôt que
« plancher » ou « log-only » : stocker `base*` **et** abandonner le filtre
`is_active` pour le calcul de saison. L'attendu redevient calculable exactement
(`base + Σ(validations en fenêtre)`), le filet bidirectionnel de V2.42 est
**préservé**.

**Livré**
- **Bouton admin « Redémarrer la saison maintenant »** (`AdminSeasonConfig.tsx`) :
  profils d'abord (recompute `base*` + `season.*` via `recomputeSeasonBaseline`,
  pur, testé ; `updateDoc` chemins pointés, idempotent), fenêtre en dernier
  (`cloturee: false`). Itère `classement_profiles`. Aucune règle (l'admin peut
  déjà écrire ces docs).
- **`ClientDaily.tsx`** : la porte de saison teste le `createdAt` de la validation
  (plus « aujourd'hui »).
- **`reconcile-classement-profiles.js`** : **ne filtre plus `is_active` du tout**
  (`loadDailyColorById`), all-time **et** saison — les deux sont des compteurs
  d'accumulation, un bloc retiré garde ses points. Avant, la réconciliation
  retirait ces points au all-time (journal V2.53 : « −360 points »), décroissance
  inexpliquée et incohérente avec le compteur stocké. Saison ignorée si pas de
  `season.baseScore`.
- **`compute-classement-saison.js`** : la clôture remet aussi `base*` à zéro ;
  `batch.update` chemins pointés au lieu de `set(merge)` (bug orphan-key latent
  V2.53, jamais déclenché).

**Extension all-time monotone** : ton §3 (« hors périmètre, à trancher ») — tranché
par l'utilisateur (« corrige d'abord le all-time sur la même logique »), intégré au

## 4 bis. V2.57 — Bandeau de mise à jour PWA (ton plan)

**Le symptôme** : après un déploiement, il fallait vider le cache Chrome (PC) et,
sur Android, fermer tous les onglets + tirer 2-3 fois pour finir par obtenir la
nouvelle version.

**Ta cause** : `registerType: 'autoUpdate'` active bien le nouveau service worker
tout seul, mais **ne recharge pas la page** — le JS en mémoire reste l'ancien.
Diagnostic confirmé (`onNeedRefresh` ne se déclenche qu'en mode `'prompt'` ; en
`autoUpdate` la seule sortie est un `window.location.reload()` d'office, jamais
appelé au bon moment sur une PWA installée qu'on ne ferme pas).

**Livré** (`components/UpdateBanner.tsx`, monté dans `main.tsx` à côté de `Navbar`) :

- `useRegisterSW` (`virtual:pwa-register/react`). On **garde `autoUpdate`** et on
  passe **`onNeedReload`** — l'option prévue pour ça (« Called when the service
  worker has taken control and the page would normally reload. Useful to fully
  control the reload flow. »). Elle **intercepte** le rechargement d'office et
  affiche un `Snackbar` MUI non auto-fermant : « Une nouvelle version est
  disponible » + **Mettre à jour** (→ `reload()`) / **Plus tard** (ferme ; la MAJ
  s'applique au prochain démarrage complet). Un rechargement d'office serait
  néfaste sur l'écran TV ou pendant une saisie d'essais.
- **Deux déclencheurs de `registration.update()`** : `visibilitychange` (après
  ≥ 3 min en arrière-plan) + intervalle horaire. Sans ça, une PWA installée jamais
  fermée ignore une version des jours durant. Requête vers `sw.js` (`no-cache`,
  quelques centaines d'octets), **zéro lecture Firestore**.
- **Pas de bandeau** sur `/admin/competitions/live-display/:competitionId`
  (écran TV sans personne devant — le repère de version en coin suffit).
- `vite:preloadError` de `main.tsx` **conservé** (filet de dernier recours).
- **§4 du plan** : `curl -I` sur un asset hashé → `cache-control: …, immutable`
  déjà appliqué → `firebase.json` **non touché**.
- Docs : `CLAUDE.md` (section cache PWA), `ClientHelp.tsx` (nouvelle section
  « Nouvelle version disponible »), `changelog.ts` (entrée V2.57).

**Limite** : le bandeau ne peut apparaître **qu'entre deux versions**. Les clients
encore sur 2.56.1 seront auto-rechargés par leur ancien service worker ; le bandeau
démarre à partir de la transition **2.57 → version suivante**. Vérification = test
manuel sur deux déploiements successifs (protocole §5 du plan) — **pas d'e2e
possible**, le test manuel est le bon niveau.

## 6 bis. Vérification du déploiement en ligne + en-têtes de cache

Contrôle demandé par l'utilisateur — la mise en ligne est effective et le cache est
configuré comme prévu. *(Fait d'abord sur V2.56.1 / `index-Dhomuelf.js` ; refait
après le déploiement V2.57, mêmes conclusions, bundle `index-BigVcQjH.js`.)*

**Version servie** : `curl https://blocabrac.web.app/` référence le bundle hashé
courant, qui contient la chaîne de version attendue → c'est bien la dernière build
qui est en ligne (le n° affiché en Navbar).

**`curl -I https://blocabrac.web.app/assets/index-Dhomuelf.js`** :

```
HTTP/2 200
cache-control: public, max-age=31536000, immutable
content-type: text/javascript; charset=utf-8
last-modified: Sun, 06 Sep 2026 13:54:12 GMT      ← heure du deploy
content-length: 134833
x-cache: HIT                                      ← servi depuis le CDN Fastly
```

- `200` : le fichier hashé est servi.
- `immutable, max-age=1 an` sur `/assets/**` : conforme à `firebase.json`. Sans
  risque d'obsolescence — le **nom** du fichier change à chaque build (hash Vite),
  et `index.html` (qui pointe vers le nouveau nom) est servi en `no-cache`
  (`source: "**"` → `Cache-Control: no-cache` dans `firebase.json`).
- La seule couche qui peut encore servir du périmé côté client est le **service
  worker** de la PWA (cache distinct du cache HTTP) — résolu par fermeture/réouverture
  de l'appli, rechargement forcé, ou déconnexion/reconnexion (qui passe par
  `terminate` + `clearIndexedDbPersistence` + `reload`, cf. `Navbar.tsx`).

**Conclusion** : rien à faire côté serveur. Le déploiement est propre.
