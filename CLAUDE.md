# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Blocabrac PWA: a French climbing-gym management app (Firebase project `blocabrac`, hosting at `blocabrac.web.app`). React + TypeScript + Vite + MUI frontend, no backend server — the frontend talks directly to Firestore/Auth, with all access control enforced in `firestore.rules`. There are no Cloud Functions.

## Commands

All commands run from `frontend/` (the actual app lives there, not at repo root):

```bash
npm run dev              # Vite dev server
npm run build            # tsc -b && vite build — always run before considering a change done
npm run lint             # eslint .
npm test                 # vitest run — fast unit tests (src/**/*.test.ts), no external deps
npm run test:watch       # vitest in watch mode
npm run test:rules       # Firestore security-rules tests, requires the Firebase emulator (needs Java)
```

- Run a single unit test file: `npx vitest run src/utils/climbingPoints.test.ts`
- `npm run test:rules` wraps `firebase-tools emulators:exec` around `vitest --config vitest.rules.config.ts` (tests live in `frontend/test/`, not `frontend/src/`) — this is why it's a separate npm script and a separate vitest config from `npm test`.
- Deploy from the repo root (not `frontend/`): `npx firebase-tools deploy --only hosting` or `--only firestore:rules` (or both) — `firebase.json` points hosting at `frontend/dist`. `firebase login` needs a real interactive terminal, not this CLI's sandboxed shell.
- Before a `firestore.indexes.json` deploy, diff it against what's actually live — it has drifted from prod before.

## Architecture

### Roles and the `roles` vs `role` field

Every account has a role set (`admin`, `ouvreur`, `moniteur`, `client` — combinable, e.g. a moniteur account is also always `client`). Current accounts store this as an array field `roles: string[]`; some legacy accounts still only have a scalar `role: string`. **Never query or check role by the scalar `role` field alone** — always merge both. The canonical patterns are:
- Firestore rules: `isUserRole(role)` in `firestore.rules` (checks `roles` array OR legacy `role` string).
- Frontend: `ProtectedRoute.tsx` and `Navbar.tsx` both merge `roles` + legacy `role` into a `Set` before checking access.
- Any new query that needs "all users with role X" must do the same two-branch merge (see `MessagesList.tsx` for the pattern: two `getDocs` calls, one `where('role','==',X)`, one `where('roles','array-contains',X)`, merged by doc id).

Every account is always guaranteed to have `client` in its roles (enforced in `AdminUsers.tsx` and mirrored server-side by `hasClientRole()` in rules) — the "client" area is not staff-exclusive-free, it hosts features (like "Potes de grimpe") open to everyone including staff.

### `age` vs `dateOfBirth` — a deliberately accepted legacy field, not a `role`/`role`s-style divergence

`users.dateOfBirth` (ISO date, collected at registration since V2.4x) is the only field any write path still populates; the older `users.age` (a number, frozen at whatever it was when entered — wrong as soon as the person has a birthday) is never written by current code anywhere in the app. `utils/ageCategory.ts`'s `getSeasonAge(dateOfBirth, legacyAge, referenceDate)` is the single place that derives an age — it prefers `dateOfBirth`, falling back to the legacy number only when a given account has never had a date entered. Every TypeScript `User`/`Participant`-shaped interface that reads this fallback names the field `legacyAge`, not `age` — the name itself is the warning not to write it, since it's read in repli only; the underlying Firestore field is still literally `age` (never renamed in the 11 legacy documents that still carry it, there is nothing to gain from a data migration that cannot reconstruct a birth date from a frozen age anyway). This is why it is *not* the same failure mode as the `role`/`roles` split above: that one had multiple write sites racing to keep two fields in sync; this one has exactly one direction of truth and zero remaining writers of the old field.

### Boulders: one collection, several lifecycles

All climbing routes (daily wall routes and competition routes) live in a single `boulders` collection, discriminated by `type: 'daily' | 'competition'`:

> ⚠️ **Never delete a `boulders` document.** Deactivation (`is_active: false`, set by `DailyBoulderForm.tsx`) is the *only* retirement path — a wall rotation never removes docs (grep-verified V2.54). The monotonicity of both the all-time **and** the season classement scores depends on this: since V2.56 the reconciliation counts a validation as long as its boulder doc exists (at the boulder's last-known colour), so a hard delete would make every associated validation — and its points — vanish at once. `client_boulder_results`, `client_badges`, and every stats/classement page also assume the doc stays readable forever. If a test/mistake boulder must go, deactivate it; a manual delete from the Firebase console is a data-integrity break, not a cleanup.


- **Daily boulders** (`type: 'daily'`): managed per-wall in `Ouvreur/DailyBoulders/`, shown to clients in `Client/Daily/ClientDaily.tsx`. Color (`color` field) is always visible. `is_child_route: boolean` marks a "ouistiti" route (children's route physically marked with a monkey icon instead of the color logo) — it exists across the full color range, it is not a separate color.
- **Official "grosse compétition" boulders** (`type: 'competition'`): created via `Ouvreur/CompetitionBoulders/CompetitionBoulderForm.tsx`, tied to a `competitions` doc via `competition_id`. Their real cotation (`difficulty` field) is hidden from climbers during the event — the validation screen (`Client/Competitions/ClientCompetitions.tsx`) never displays it, climbers just mark success/attempts blind ("Mystère"). Scoring reads `difficulty` live.
- **Reused daily boulders in a "compétition régulière"**: a level-restricted competition (via `minLevel`/`maxLevel` on the `competitions` doc) that runs for weeks on walls that are never stripped, built from *existing* daily boulders instead of new hidden ones. These boulders stay `type: 'daily'` forever and gain `competition_id` + `competition_active: true` while tagged in. `competition_active` is the field that matters here — it's what distinguishes "currently an active member of this competition" from a boulder that merely still carries an old `competition_id` for historical stats. **`competition_id` is never cleared** once set (on either boulder kind) — every stats/classement page reconstructs a competition's results by querying boulders on `competition_id` alone, with no `type` filter.
- "Terminer la compétition" (`Ouvreur/CompetitionBoulders/CompetitionBouldersList.tsx`) ends a competition's boulder lifecycle: `type:'competition'` boulders become `type:'daily'` (their hidden cotation becomes the public `color`, to be re-graded from climber feedback); reused daily boulders just lose `competition_active`. The competition's own `status` field is a separate, manually-controlled admin action — this button never touches it.

### Boulder images: Cloudinary, `image_public_id` first, `image_base64` as fallback

Boulder photos are uploaded to Cloudinary (unsigned preset, folder `blocabrac/boulders`) instead of stored as base64 in Firestore — the free Spark plan's 10 GiB/month egress quota can't survive serving inline images to every wall view. `services/imageStorage.ts` is the **only** file allowed to import/call Cloudinary (`uploadBoulderImage`, `getBoulderImageUrl`, `deleteUnconfirmedUpload`) — swapping providers later means rewriting only that module. New boulders write `image_public_id`; the legacy `image_base64` field is never written again but is kept as a read-time fallback (`image_public_id ? getBoulderImageUrl(...) : image_base64`) wherever a boulder image is rendered — every such site must implement both branches, a screen that only checks one will show broken images for the other kind of boulder. `getBoulderImageUrl(publicId, 'thumb' | 'full')` composes the URL from Cloudinary transformation strings (`f_auto,q_auto,w_400`/`w_1000`) rather than storing pre-built URLs, so there's nothing to keep in sync if the transformation recipe changes.

The annotation dots (start/end holds) are baked into the image raster at save time (`canvas.toDataURL()` in `DailyBoulderForm.tsx`/`CompetitionBoulderForm.tsx`) — the `annotations` field in Firestore is write-only after creation (read back only when re-editing that same boulder), never used to render an overlay at display time. This is why the Cloudinary upload happens at submit time, not on file selection: the final image doesn't exist until the ouvreur has finished placing the dots, so "upload immediately to hide latency" isn't compatible with baking annotations into the raster. Editing an existing boulder without picking a new photo skips the upload entirely and leaves `image_public_id` untouched (Firestore `updateDoc` only touches keys present in the payload).

`firestore-migration/migrate-boulder-images-to-cloudinary.js` is the one-time backfill for boulders created before this change: Passe A (default) uploads existing `image_base64` to Cloudinary and writes `image_public_id`, keeping the base64 as-is; Passe B (`--delete-base64`, run manually later after visual verification in prod) removes the now-redundant base64 field.

`scripts/cleanup-orphan-boulder-images.js` runs monthly via `.github/workflows/cleanup-orphan-boulder-images.yml` (cron + `workflow_dispatch`) to delete Cloudinary images no longer referenced by any `boulders` doc. It lives in `scripts/` (tracked by git) rather than `firestore-migration/` (entirely gitignored) specifically so `actions/checkout` in CI actually has the file to run — a script that only exists locally can't be checked out on a fresh CI runner. It deliberately queries `boulders` with **no filter** on `is_active`/`type`/`competition_active` — a deactivated boulder (`is_active: false`) or one whose competition ended still keeps its image referenced for historical stats, and a filtered query would wrongly treat that image as orphaned. Guardrails: dry-run unless `--delete`, never touches a Cloudinary resource younger than 7 days, and aborts if the reference count drops both more than 20% **and** by at least 20 references versus the last run (likely a partial read or auth failure, not real deletions) — both conditions must hold so a legitimate sector rotation (one wall's ~15 boulders pulled at once) doesn't trip it at low total boulder counts; `--force`/`--accept-drop` bypasses the abort explicitly when the drop is legitimate, instead of hand-editing the state file. If `cleanup-state/state.json` doesn't exist yet (first run, or a lost file), the guard is skipped with an explicit log line rather than silently — there's nothing to compare against. That comparison's state lives in `cleanup-state/` (also tracked by git) because it must survive across ephemeral CI runs; the workflow commits it back after each execution. Credentials come from env vars in CI (`FIREBASE_SERVICE_ACCOUNT_JSON`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` — GitHub secrets) or local gitignored files in `firestore-migration/` when run manually from the Codespace (`serviceAccountKey.json`, `cloudinary-admin-credentials.json`). **`state.json`/`orphan-images-log.json` are emulator-aware** (V2.51, extending the same fix from `reconcile-classement-profiles.js` — see the `classement_profiles` section below): both paths derive from `FIRESTORE_EMULATOR_HOST`, writing `*.emulator.json` (gitignored) instead of the tracked production files whenever it's set — the risk here is sharper than for the reconciliation log, since `state.json` is exactly what the drop-guard above compares against.

`--backup <dossier>` (same script) downloads every currently-referenced Cloudinary image to a local folder — idempotent (skips files already present, matched by sanitized public_id regardless of extension) and writes a `manifest.json` mapping `public_id → boulder_id → filename`. Exists because since Passe B removed `image_base64`, each boulder photo's only copy lives on a free-tier third-party account with no backup of its own. Manual/occasional use only for now (not wired into the CI workflow) — where to store the archive durably is still an open decision, deferred until the multi-gym (white-label) push where the volume will actually matter.

### `competition_results` — written live, then locked

`ClientCompetitions.tsx` writes each boulder validation to `competition_results` immediately (`setDoc(..., {merge:true})`) rather than buffering in React state until submit — a discharged tab or a reload must never lose a validation. The success/fail click writes immediately; the repeated-entry fields (attempts, rating, proposed cotation) are debounced ~800ms to avoid a write per `Select` interaction. On opening the validation dialog, existing results for that user+competition are re-fetched to repopulate the UI (this is what makes a reload safe, not just the debounce). "Soumettre les résultats" is a **lock**, not a submit: a single `writeBatch` sets `submitted: true` + `submitted_at` on every result doc for that competition, and `firestore.rules` then refuses any further `update`/`create` by the owning client on a doc with `submitted: true` (admin/ouvreur keep unrestricted write access — deliberate status quo, see `PLAN-spark-images-competition.md` "Écart à trancher"). Once locked, the dialog goes read-only client-side too, but the enforcement that matters is server-side.

### Firestore persistent cache (IndexedDB) and the two cache layers

`firebaseConfig.ts` initializes Firestore with `persistentLocalCache({ tabManager: persistentMultipleTabManager() })` (Chantier 3) instead of the default in-memory cache — decisive on competition day so re-opening the app doesn't re-transfer unchanged boulder images, and so validations queue locally and replay on reconnect if the venue's indoor coverage drops. `persistentMultipleTabManager()` is mandatory: without it, activation throws as soon as a second tab is open, which is exactly the admin's TV-display setup (two windows). Persistence is force-disabled (falls back to plain `initializeFirestore(app, {})`) whenever `MODE === 'test'` or `VITE_USE_EMULATOR === 'true'` — Firestore security rules aren't re-checked against cached reads, so a stale cache entry could silently pass what a live read would reject, masking a real permission bug in Playwright.

IndexedDB is scoped to the site origin, not to the signed-in account — on a shared device (admin's workstation, a borrowed phone), a previous account's cached data would otherwise survive logout. `Navbar.tsx`'s `handleLogout` (both the desktop button and the mobile drawer item route through it) enforces the exact required order: `auth.signOut()` → `terminate(db)` → `clearIndexedDbPersistence(db)` → `window.location.reload()`. `clearIndexedDbPersistence` only works while Firestore is inactive, and the SDK instance is unusable after `terminate()`, hence the reload. If a new logout entry point is ever added, it must go through this same function, not a bare `auth.signOut()`.

Two independent cache layers now sit in front of the app: `vite-plugin-pwa`'s service worker (static assets/shell) and this Firestore IndexedDB cache (data). If something looks frozen/stale, check which layer is responsible before assuming a code bug — a stuck UI after a data change is usually the Firestore cache, a stuck UI after a deploy is usually the service worker.

**Update banner (V2.57→V2.58, `components/UpdateBanner.tsx`, mounted in `main.tsx` next to `Navbar`; mode switched to `'prompt'` in V2.62, `CORRECTIF-bandeau-mode-prompt.md`)**: V2.57/V2.58 used `registerType: 'autoUpdate'` + `onNeedReload`, an **event** fired when the new SW takes control while the page is running — on a PC tab left open for hours, React always won the race against that event and the banner worked. On an Android cold start, the sequence (fetch `sw.js` → install → **activate immediately**, `skipWaiting` being intrinsic to `autoUpdate`) can complete *before* `UpdateBanner` even mounts — the event fires into a void, no listener catches it, and the app silently loads the new version on the next reload with no banner ever shown. Confirmed in prod (2.60→2.61: PC banner worked, Android never showed it, a pull-to-refresh jumped straight to the new version). This was foreseeable: `autoUpdate` is *designed* to reload on its own, and intercepting that is fighting an automatic mechanism into acting like a manual one — a race that isn't guaranteed to resolve in the app's favor.
- **Fix: `registerType: 'prompt'`** (`vite.config.ts`). In this mode the new SW stays **`waiting`** instead of self-activating — a durable *state*, not a fugitive event, so it doesn't matter when `UpdateBanner` mounts: it reads `needRefresh` (the boolean pair from `useRegisterSW`, `[needRefresh]`) and finds a waiting SW if one exists. "Mettre à jour" calls `updateServiceWorker(true)`, which activates the SW **and** reloads in one call — `onNeedReload`/`window.location.reload()` are gone, there's nothing left to intercept.
- **Trade-off that comes with `prompt`, by design, not a bug**: nothing forces the update anymore — as long as nobody clicks, the old version keeps being served indefinitely (unlike `autoUpdate`, which eventually imposed the new version on the next reload regardless). The Navbar version marker stays the diagnostic for "is this device actually up to date". Not mitigated further for now (a non-dismissible banner or a forced-after-N-days variant was considered and deliberately deferred — see the same `.md`) — start simple, watch real usage first.
- **A version's *own* registration mode governs its own transition, not the mode of the version it's replacing** — the SW currently deployed decides whether *its own successor* is auto-activated or held waiting. A version shipped with `autoUpdate` (like every one through V2.61) will still auto-activate whatever comes right after it, `prompt` or not; the `prompt` behavior only takes effect starting from the transition *after* the one where it was introduced (2.62→2.63 here, not 2.61→2.62) — the exact same one-version lag already seen with the banner's own introduction at V2.57→V2.58. Don't conclude "the fix doesn't work" from testing on the wrong transition.
- registers **two `registration.update()` triggers** — `visibilitychange` (only after ≥3 min in the background, so the climber reopening the app in the gym re-checks) and an hourly `setInterval` (for a PWA left open). Without these, an installed PWA that's never closed can ignore a version for days, because the browser only checks for a new SW on page load and throttles it. With `prompt`, these triggers also matter for *making the waiting SW show up sooner*, not just for detecting one. `registration.update()` is a few hundred bytes over the network (`sw.js`, `no-cache`), **zero Firestore reads**. Any change to the SW registration must keep both triggers.
- is **not rendered on `/admin/competitions/live-display/:competitionId`** (the unattended TV screen — the corner version marker is enough there).
- `main.tsx`'s `vite:preloadError` reload guard stays — it's the last-resort net for a stale `index.html` pointing at a deleted chunk. It matters *more* under `prompt` than it did under `autoUpdate`, precisely because an old version can now persist far longer if nobody clicks the banner. Verifying the banner needs a **manual test across two successive deploys** (deploy N, deploy N+1, confirm the banner appears without clearing anything) — a Playwright e2e can't simulate an intermediate deploy, don't write one. The real test for the `prompt` fix specifically is a **cold start** on Android (app fully closed, then reopened on the version right after the one that introduced `prompt`) — that's the exact case that failed under `autoUpdate` and the only one that validates the fix; the PC/backgrounded-app cases were already working before and only confirm nothing broke.

### Mini-compétitions (moniteur) — a third, unrelated system

`mini_competitions` is a **separate collection**, not part of the boulders/competitions system above. A moniteur builds one by picking existing daily boulders (by wall/color), and it's referenced by id from a `courses` (séance) doc's `miniCompetitions: string[]` array — same shape as that doc's `exercises: string[]`. Results are written to `client_course_results` (the same collection exercises use) with `boulderId`/`boulderColor`/`miniCompetitionId` fields; `boulderColor` is snapshotted at validation time so a later re-grade doesn't retroactively change past scores. Ranking is computed client-side in `Moniteur/Stats/StatsList.tsx` from `climbingPoints.ts`.

### Course sessions (`courses` collection) and the scheduled/active/archived lifecycle

A `courses` doc (called "séance" in the UI) goes through `scheduled → active → archived`, driven by `activatedAt`/`archivedAt` timestamps (see `utils/courseSessionStatus.ts` for the client-side status derivation, mirrored server-side by `canValidateCourse()` in rules). Content (exercises, mini-compétitions) is only fetched/shown to clients once a session leaves `scheduled` — "objectifs visibles, contenu caché" until activation. Participants default to the whole group (`Participants: string[]`), with individual opt-out (`optedOut: string[]`) only allowed before activation.

### Cross-user visibility: the `classement_profiles` mirroring pattern

Firestore rules only let a client read their own `users` doc — clients cannot list other clients' results directly. Anywhere the app needs to show one client data derived from another (leaderboard, friends' status), the *source* client mirrors a small summary onto a separate, broadly-readable doc keyed by their own uid (e.g. `classement_profiles/{uid}`), computed and written by themselves on their own activity. Reuse this pattern — do not try to grant broader read rules on `users` or per-user result collections to solve a "show me other users' data" need.

⚠️ **Mirror only what the reader actually consumes, never a whole source field "because it's already there".** `classement_profiles` briefly carried the client's raw `dateOfBirth` (added alongside the field's introduction in `users`, mirrored by habit rather than by need) even though its only reader (`ClientClassement.tsx`) has always just needed a derived FFME age category, never the exact date — an unforced exposure of minors' birth dates to every authenticated account, found and fixed 2026-08-17 (`SUIVI-date-de-naissance.md`/`RETOUR-date-de-naissance-avant-modifs.md`, `HANDOFF-date-de-naissance-2026-08-17.md`). Fixed by writing the derived `ffmeCategory` string instead (still computed with `getFfmeCategory(getSeasonAge(...))`, just computed at write time rather than read time) and never writing `dateOfBirth` to this collection again — restricting the read rule was rejected, since the leaderboard's whole reason to exist is reading other clients' profiles. Before adding any new field to a mirrored doc, ask what the reader needs, not what the source doc happens to have.

### `classement_profiles`: incremental counter, never a full-history recompute

`classement_profiles/{uid}`'s score fields (`score`, `bouldersValidated`, `bestColorRank`, `colorCounts`) are maintained **incrementally** by `ClientDaily.tsx` — a validation reads only *its own* prior state (a single `getDoc` on `client_boulder_results/{uid}_{boulderId}`, deterministic ID) and applies a delta inside a `runTransaction`, never a `getDocs` over the client's full history. This replaced an earlier design (V2.26–V2.28) that preloaded the entire success history into memory at mount — correct, but its read cost grew unboundedly with account age, the one metric in the whole app that got worse over time by itself (see `CONCEPTION-selecteur-marge-compteur-incremental.md` §3 for the full reasoning).

- `colorCounts: Partial<Record<Level, number>>` is the **only** source of truth for `bouldersValidated`/`bestColorRank` — both are *derived* from it (`summaryFromColorCounts` in `utils/classementScore.ts`), never incremented independently, so there's only one place drift can originate. `score` deltas are computed by `scoreDeltaForValidation` (old points vs new points for that one boulder) and applied via the transaction's read-then-write, not `increment()` — needed because `bestColorRank` requires reading the current `colorCounts` anyway to recompute after the delta.
- The color used for a validation's points is always the boulder's **current** color (`colorById`, from the currently-active `boulders` fetched at mount), never a value frozen at validation time — `client_boulder_results` doesn't store color at all. Recoloring a boulder therefore no longer retroactively updates every past validation's contribution on next page load (the old full-recompute design did this side-effect by accident); only that boulder's *next* validation picks up the new color. This is a deliberate trade-off, not a bug — see the reconciliation script below for the tool to resync if a bulk recolor ever needs to be reflected immediately.
- A deactivated boulder (`is_active: false`) drops out of `ClientDaily.tsx`'s `colorById` (fetched active-only at mount), so a previously-validated-then-deactivated boulder's contribution **freezes** in the stored counter — it is never subtracted. Since V2.56 the reconciliation script agrees: **both `score`/`colorCounts` (all-time) and `season.*` are accumulation counters — a validation of a boulder that has since been rotated out still counts**, at the boulder's last-known colour (`reconcile-classement-profiles.js`'s `loadDailyColorById` has no `is_active` filter). Before V2.56 the monthly reconciliation stripped those points (`--360 points, 1 rouge on a since-deactivated boulder` in the V2.53 log) — a silent decrease nobody could explain, and inconsistent with the stored counter that already froze them. The boulder *doc* is never deleted (rotation is `updateDoc(..., {is_active:false})`), so its colour stays readable.
- **`scripts/reconcile-classement-profiles.js`** is the non-optional safety net for any incremental counter (per this project's own convention, see `cleanup-orphan-boulder-images.js`): recomputes the expected profile from `client_boulder_results` (the real source of truth) for every account in `users` — not every doc in `classement_profiles`, since a legacy account created before this mirroring pattern existed may have **no** profile doc at all (this was true for all 12 real accounts in prod until this script's `--fix` backfilled the one with actual validated results on 2026-08-16 — worth rerunning occasionally, not just after a suspected drift). Dry-run by default, `--fix` to write, `--uid <uid>` to check a single account. **`colorCounts` write removes orphan keys (V2.53)**: corrections go out as `set(update, { merge: true })`, which *merges* maps and never removes a key — so a stale colour key (e.g. a boulder recoloured `"noire"` → `"noir"`, leaving `colorCounts.noire` behind) survived every pass and the profile stayed "en écart" forever. `colorCountsWriteValue(stored, expected)` now adds an explicit `FieldValue.delete()` for every key in stored but not expected, for both `colorCounts` and `season.colorCounts`. Emulator regression test: `frontend/test/reconcile-orphan-key-emulator.mjs`. Runs automatically via `.github/workflows/reconcile-classement-profiles.yml` (monthly cron + `workflow_dispatch`, same pattern as `cleanup-orphan-boulder-images.yml`), journaling every drift found to `cleanup-state/classement-profiles-reconcile-log.json` (committed back by the workflow) whether or not anything gets written. **Drop-guard** (added 2026-08-16 on review feedback): the diff pass always runs *before* any write, and `--fix` aborts with no writes and a non-zero exit (visible workflow failure) if drift affects more than 30% of accounts **and** at least 3 accounts — the original "a drift is corrective by construction" reasoning only holds for a genuine data drift, not for a bug in the reconciliation script's own recompute (or an unreflected barème change), which would otherwise get silently propagated to every profile by the monthly cron. `--force` bypasses the guard explicitly (same escape hatch as `cleanup-orphan-boulder-images.js`); `--uid` (single-account debugging) skips it too, since a lone account has no "proportion" to evaluate. **Journal jamais partagé avec l'émulateur** (retour ClaudeNav 2026-08-19, PROCESSUS-erreurs-avalees.md) : the log path is derived from `FIRESTORE_EMULATOR_HOST` — when set (any local e2e run that invokes this script, e.g. `e2e-season-classement-flow.mjs`), it writes to `classement-profiles-reconcile-log.emulator.json` instead, gitignored (`cleanup-state/.gitignore`), never the tracked production log. Found the hard way: a local e2e run had already overwritten the real log with emulator uids once, caught only by chance via `git status` before a commit. **Same guard extended to `cleanup-orphan-boulder-images.js`'s `state.json`/`orphan-images-log.json`** (asked for explicitly by ClaudeNav, risk judged *more* severe there since `state.json` directly feeds that script's drop-guard comparison against the previous run — an emulator-polluted reference count could make the guard fire on nothing or, worse, miss a real drop) — verified by hashing `state.json` before/after a real dry-run against the emulator, unchanged. **`compute-classement-saison.js` has no local tracked state/log file at all** (checked, not assumed) — everything it reports goes through `console.log` (captured by the CI run log, never a committed file) and its real writes land in Firestore itself, already correctly scoped to whichever project the Admin SDK is pointed at; nothing to extend this guard to there. None of the three `.github/workflows/*.yml` set `FIRESTORE_EMULATOR_HOST` (confirmed by grep, not assumed) — in CI all three scripts always write their real production state/log files.

### Seasonal classement (`season.*`) and the end-of-season Finale — a second counter, not a replacement

`classement_profiles/{uid}.season.{colorCounts,score}` (V2.4x, see `CONCEPTION-classement-saisonnier.md`) is a **second, independent incremental counter**, added deliberately alongside the all-time one above rather than replacing it — a seasonal bound on the all-time fields was already evaluated and rejected in V2.26 (it would have understated lifetime `score`/`bouldersValidated`, which are meant to track progression forever). The season counter exists for a different purpose: determining who qualifies for a "Finale de l'année" (the small `officiel`/FFME-mode competition, see below), which needs a bounded time window, not a lifetime total.

- **Season window is admin-configurable, never hardcoded** — `app_config/classement_saison` (`debut`/`fin`, ISO dates, plus `cloturee: boolean`), edited via `AdminSeasonConfig.tsx` (`/admin/season-config`). This exists because the app's actual launch date didn't align with the conventional "1er septembre" season start, and rather than hardcode a date and special-case the first season, the window is just data the admin sets once. `ClientDaily.tsx` reads it once at mount (a single `getDoc`, cached in a ref — never per-validation) and applies the *same* delta already computed for the all-time counter (`scoreDeltaForValidation`/`summaryFromColorCounts`, see `utils/classementScore.ts`) to `season.*` as well, but **only if "now" falls within `[debut, fin]`** (`isWithinSeasonWindow`, pure and unit-tested). Outside the window (summer, or no window configured yet), only the all-time counter moves — a grimpeur's personal progression stat never stops accumulating, only the seasonal qualification counter pauses.
- **`classementOptIn` gates qualification too, not just public visibility**: a grimpeur who opts out of the public classement (`ClientProfile.tsx`) is also excluded from the season's top-10 selection, even at a qualifying score — refusing the public classement is treated as refusing the Finale too (decided explicitly, not a side effect nobody chose). The opt-in toggle's help text says so.
- **Live season standings cost zero extra reads**: `ClientClassement.tsx` already does one unfiltered `getDocs` over `classement_profiles` for the all-time leaderboard; `season.score`/`season.colorCounts` live on the same documents, so a "Classement de saison" toggle is purely a client-side re-sort/re-render of data already in memory, not a second query.
- **End of season**: `scripts/compute-classement-saison.js` runs daily via `.github/workflows/compute-classement-saison.yml --fix` (a daily cron rather than one fixed date, precisely because the window is admin-configurable and unpredictable) but only actually acts once `fin` has passed **and** `cloturee` isn't already `true` — otherwise it's a no-op, checked every run. **Simulation by default, `--fix` to write** (ClaudeNav review, 2026-08-17): this is the most destructive of the project's three maintenance scripts (an irreversible reset), so it follows the same dry-run-unless-told-otherwise convention as `reconcile-classement-profiles.js`/`cleanup-orphan-boulder-images.js` rather than the inverted default it originally shipped with — without `--fix` it prints the computed top 10/10 and how many profiles would be zeroed, writing nothing. When it does act (`--fix`): separates opted-in profiles by `gender`, ranks by `(season.score desc, totalBouldersSeason desc)` — the tie-break the user chose — takes the top 10 of each (all ties at the cutoff included, never an arbitrary cut), writes the result to `classement_saisons/{"YYYY-YYYY"}` (read-only to clients, write-only via the Admin SDK — nothing in `firestore.rules` opens a client write path to it), sets `cloturee: true` + `cloturee_at` (ISO timestamp), and **only then** resets every profile's `season.*` to zero — archive-then-reset, never the reverse, because unlike the all-time counter's reconciliation ("a drift is corrective by construction"), a premature reset here would be real, unrecoverable data loss.
- **`cloturee` is the guard that stops the monthly all-time reconciliation from undoing the season reset**: if `reconcile-classement-profiles.js` recomputed `season.*` from `client_boulder_results` while `cloturee` is still `true` (the admin hasn't reconfigured next season's window yet), it would see the just-reset zeros as "drift" against the *old* `[debut, fin]` still on record and "correct" them back — silently undoing the reset. So the reconciliation script skips `season.*` (and only that) entirely whenever `cloturee` is `true`; reconfiguring the window (which the admin does as one normal save in `AdminSeasonConfig.tsx`, clearing `cloturee_at` too via `deleteField()`) clears the flag and re-enables it. The same script also reconciles `season.*`/`gender` against `client_boulder_results`/`users` under the same dry-run/`--fix`/drift-guard discipline as the all-time fields — a validation counts toward a season based on its `client_boulder_results.createdAt`, which is why that field had to first be made immutable (see below) before this reconciliation could be trusted at all.
- **A forgotten reconfiguration is otherwise silent** (ClaudeNav review, 2026-08-17): the symptom — everyone at zero in the "Classement de saison" tab — is indistinguishable from a normal season start, and by the time anyone notices, the missed validations can't be recovered (reconciliation only ever recomputes against the *current* window). `AdminSeasonConfig.tsx` shows a warning banner whenever `cloturee` is `true`. That alone isn't enough — nobody reads the logs of a cron that stays green — so `compute-classement-saison.js` also fails the workflow loudly (non-zero exit) once `cloturee_at` is more than `RECONFIGURATION_GRACE_DAYS` (7) days old, rather than silently no-op-ing forever.
- **`client_boulder_results.createdAt` immutability was a prerequisite, not a side project**: before this chantier, `createdAt` was silently reset to "now" on every edit of a boulder result (same `setDoc` call as `updatedAt`), so it never actually meant "when was this first validated." That was harmless while nothing read it, but the season reconciliation above needs exactly that meaning to decide which season an old validation belongs to. `ClientDaily.tsx`'s `resolvePreviousResultState` (renamed from the classement-only `resolvePreviousClassementState`) now reads the existing document's `createdAt` before every write and carries it forward unchanged; `updatedAt` still updates every time. This read now runs unconditionally (previously gated on the boulder having an active color), since `createdAt` must be preserved even for boulders without a resolvable color. Verified (ClaudeNav review, 2026-08-17) to be the *only* two write sites for this collection project-wide — no admin screen, migration script, or other path writes it.
- **Roster generation is a manual admin action, not automatic**: a "Générer le roster" button (`AdminCompetitionManagement.tsx`, shown only for `scoring_mode === 'officiel'` competitions, next to "Saisie juge") reads every `classement_saisons` doc and picks the most recent by sorting IDs client-side (`"YYYY-YYYY"` compares lexicographically) — **not** `orderBy('__name__', 'desc')`, which Firestore rejects ("does not support descending key scans"), found by the e2e pass — and bulk-creates `competition_participants` for each qualified uid not already registered, with `?? null` on every optional field copied from `users` (a `setDoc` throws on `undefined`, not `null`; also fixed in the manual-add path, `AdminCompetitionRegistration.tsx`, same bug). It only seeds the roster; nothing prevents the admin from adding/removing individual participants afterward through the existing screen.

#### Season restart during rollout (V2.56) — `season.*` becomes a monotone accumulator, and the season calc drops the `is_active` filter

The season launched with the public rollout and is unfair while most climbers aren't on the app yet. `AdminSeasonConfig.tsx` gained a **"Redémarrer la saison maintenant"** button (Modèle A, `HANDOFF-redemarrage-saison-2026-09-06.md` + `RETOUR-redemarrage-saison-modele-a.md`). It is admin-operable, browser-side (admin can already write any `classement_profiles` — `isUserRole("admin")` in rules, no rules change), idempotent (dotted-path writes replace, a second click recomputes the same thing).

- **What it does, in order (profiles first, config last — deliberate):** ① load *all* daily boulders (`type=='daily'`, **no `is_active` filter**); ② for every `classement_profiles` doc, recompute `season.baseScore`/`season.baseColorCounts` **and** `season.score`/`season.colorCounts` from that climber's own `client_boulder_results` (`success:true`, original `attempts`, each boulder at its current/last-known colour) via the pure `recomputeSeasonBaseline` in `classementScore.ts`; ③ **only then** write `app_config/classement_saison` with the new `[debut, fin]` + `cloturee:false`. The reverse order would let a reconciliation pass on a not-yet-recomputed profile compute an amputated expected and write it.
- **`season.baseScore`/`season.baseColorCounts` are the frozen starting credit.** `season.score` = `base` + Σ(validations since `debut`); the incremental delta path (`ClientDaily.tsx`) adds to `season.score`/`colorCounts` as before, `base*` is never touched again until the next restart or the end-of-season close.
- **The season is now a monotone accumulator — points never go down when a wall rotates.** This is the whole point of the restart ("c'est l'idée même du changement"). Consequences:
  - **`ClientDaily.tsx`'s season gate now tests the validation's own `createdAt`, not "today"** (`applyClassementDelta(... resultCreatedAt ...)`). After a restart the entire pre-`debut` history is out-of-window, so editing/un-validating such a boulder must NOT move `season.*` (its credit lives frozen in `base*`) — the old "today ∈ window" gate would have pushed the score below the base credit. **But the `createdAt` test alone is not enough** (ClaudeNav review 2026-09-06): during the close→reconfigure gap (`cloturee: true`, up to 7 days), the window `[debut, fin]` is still the finished season's, so a validation whose `createdAt` falls in it would re-populate the just-zeroed counters. Fixed by having `fetchSeasonWindow` leave `seasonWindowRef` at `null` when `cloturee === true` (mirrors `loadSeasonWindow()`'s `if (data.cloturee) return null` server-side) — no season delta is applied at all while a season is closed. e2e-season-restart-flow.mjs step 10 exercises exactly this (validate a boulder after close → `season.*` stays 0, before and after `reconcile --fix`).
  - **`reconcile-classement-profiles.js` no longer filters on `is_active`** — one `loadDailyColorById` (`type=='daily'` only) serves *both* the all-time and the season pass. Expected season value = `storedBase + Σ(in-window validations, each boulder active-or-not, at its last-known colour)`. This keeps the V2.42 two-way reconciliation (no "floor", no "log-only") — the trick was making the expected calculable by storing `base*` and dropping the activity filter. **If a profile has no `season.baseScore` yet (no restart since V2.56 deployed), the reconciliation skips `season.*` for it entirely** (`computeExpectedProfile` returns `seasonScore: undefined`).
  - The revert vs V2.42: reconciliation used to strip removed-boulder contributions from *both* counters; now it keeps them for both (see the incremental-counter section above). The season pass additionally uses `base*` + the window filter. **First `--fix` after deploying V2.56 will *raise* the all-time score of any climber who validated a since-retired boulder** (restoring points wrongly stripped by earlier runs) — real drift for the guard, one `--force` confirms it, same as any mass realignment.
- **`compute-classement-saison.js` (end-of-season close) now zeros `season.baseScore`/`baseColorCounts` too**, else next season starts with the old credit. It also switched its reset from `batch.set(..., {merge:true})` (which does *not* empty a nested `colorCounts` map — the V2.53 orphan-key bug, latent here, never triggered since no season had closed) to `batch.update` with dotted paths (`'season.colorCounts': {}` genuinely clears it; safe because `fetchAllProfiles` gives a query snapshot so every doc exists).
- **Accounts with validations but no `classement_profiles` doc are not seeded by the button** (it iterates `classement_profiles`, not `users`) — they get their baseline on their next validation, or from the next `reconcile --fix`. In prod this is a non-case (profiles were backfilled in V2.35). Same "a climber who joined after `debut` has no starting credit" property, which is correct.

### Points scoring

`utils/climbingPoints.ts` (`calculatePoints`, `basePoints`, `deductions`) is the single shared scoring function for daily classement (`utils/classementScore.ts`) and mini-compétition classement. It scores by color string (`jaune` through `rose`), degressive by attempt count. Real "grosse compétition" boulders never use `jaune` in practice (beginner-only) even though the picker still lists it — that's intentional gym policy, not a bug. **The annual classement (`classementScore.ts`) always uses `calculatePoints` and nothing else — it has no concept of `scoring_mode` and never will**, see below.

### Competition scoring modes (`scoring_mode`) — competitions only, never the annual classement

Official/regular competitions (not the annual `classement des grimpeurs`) can pick one of four counting modes per competition, chosen via a button → menu in `AdminCompetitionManagement.tsx`, stored as `competitions.scoring_mode` (`'blocabrac' | 'blocs_valides' | 'personnalise' | 'officiel'`, defaults to `'blocabrac'` when absent). Three of the four (`blocabrac`/`blocs_valides`/`personnalise`) are **points-based** and go through `utils/climbingPoints.ts`'s `calculateCompetitionPoints` — a separate function from `calculatePoints`, never called by `classementScore.ts` or the mini-compétition path, so this feature cannot leak into the annual classement by construction. `officiel` is **not points-based at all** (see its own entry below) and has a completely separate calculation path in `competitionClassement.ts`.

- **`blocabrac`** (default): identical to the classic barème, degressive by attempt count — behaves exactly like `calculatePoints`.
- **`blocs_valides`**: each boulder carries its own `points_value` (set by the ouvreur/admin, invisible to climbers), awarded in full on success regardless of attempt count. Exists because the cotation is hidden in competition ("Mystère"), so a per-color barème doesn't reflect a boulder's actual relative difficulty — the ouvreur assigns points directly instead. For a boulder created for the event (`type: 'competition'`, `CompetitionBoulderForm.tsx`), `points_value` is a required field of that form when the competition is in this mode, and lives permanently on that competition-scoped doc. For a *reused daily boulder* (`type: 'daily'` + `competition_active`, tagged in via `CompetitionBouldersList.tsx`), `points_value` is edited inline in that list and is **cleared** (`deleteField()`) whenever the boulder leaves the competition (manual removal, or "Terminer la compétition") — the same physical boulder can be reused in a later competition with a different mode/value, so this field must never survive past this one competition's lifecycle on a shared doc.
- **`personnalise`**: a full custom barème for this competition only, stored as `competitions.custom_scoring` (`Record<color, {base, deduction}>`), editable in the same button → menu, pre-filled from the default `basePoints`/`deductions` when first opened.
- **`officiel`** (FFME/coupe du monde style): **not a points sum — a ranking**, by tops (most), then zones (most), then attempts-to-top (fewest), then attempts-to-zone (fewest) — `compareOfficialTotals` in `competitionClassement.ts`. ⚠️ **This ordering is from general IFSC/World Cup knowledge, not a reading of the current FFME rulebook** — verify before relying on it to settle a real official competition's final ranking (open item, flagged by review, never independently checked). Deliberately the **simplified** version agreed with the user (2026-08-16): a multi-key sort on totals **cumulated over the whole competition**, not the true IFSC/World Cup method (each boulder ranked independently among all competitors, those per-boulder ranks summed — a "ranking of rankings" recomputed continuously, judged too costly for the live TV screen's real-time listeners). `competition_results` gains two fields for this mode: `zone: boolean` and `attempts_to_zone: number`, written alongside `success`/`attempts` in the same debounced write `ClientCompetitions.tsx` already had (no extra write op, just two more fields on the same doc) — a top always implies the zone (`getOfficialParticipantTotals` counts it even if `zone` wasn't explicitly set, for results written before this field existed). `getOfficialParticipantTotals`/`getOfficialClassementByCategory` return `OfficialScoreEntry` (`{participant, totals: {tops, zones, attemptsToTop, attemptsToZone}}`) — a different shape from `ScoreEntry`, not a variant of it, because there's no single "score" to report. `CategoryGroup<T>` was made generic over the entry type (not just the participant) specifically to let both shapes share the same age/gender bucketing helpers (`groupByAge`/`groupByGender`) without duplicating that logic. All 3 classement screens (`AdminCompetitionStats.tsx`, `Ouvreur/CompetitionBoulders/CompetitionStats.tsx`, `AdminCompetitionLiveDisplay.tsx`) and the client validation UI (`ClientCompetitions.tsx`) branch on `scoring_mode === 'officiel'` to render tops/zones/essais columns instead of a score/points column.

  **Input consistency is enforced at entry, not after the fact** (`utils/competitionValidation.ts`'s `applyCompetitionValidationUpdate`, a pure function shared by every field in `ClientCompetitions.tsx`'s validation card, unit-tested in isolation): a top always forces the zone on, unchecking the zone always forces a recorded top back off (a top without a zone can never be saved), and attempts-to-zone is clamped to never exceed attempts-to-top — pre-filled to match it the moment the zone first becomes reached (the common case: same attempt), then re-clamped down if attempts-to-top is later corrected lower. The "essais (zone)" `Select` only offers `1..attempts` as options, reinforcing the same constraint in the UI, not just in the merge logic.

  **Ties are the normal state, not an edge case** — early in an event everyone is at 0 tops/0 zones. `rankOfficialEntries` (competition-style ranking: 1, 1, 3, not 1, 2, 3) is used everywhere an official-mode position number is shown, across all 3 classement screens.

  **The real target usage is a small "Finale de l'année" format, not a 90/35 competition** (learned 2026-08-16, after the mode was first built — see `ADDENDUM-mode-ffme-finale-annee.md`): 10 climbers, 5 boulders, single "open" category split by gender only. Two consequences that only apply to `officiel` mode:
  - **`AdminCompetitionLiveDisplay.tsx` has no rotation for this mode** — `pages`/`ROTATION_INTERVAL_MS` only ever drive the 3 points-based modes now. `officiel` renders both gender groups **side by side, permanently** (`officialGenderGroups`), each independently filtered to participants with at least one top or zone (still showing a wall of 0-0 rows would bury the one thing worth looking at) and independently ranked via `rankOfficialEntries`.
  - **Judge-entered scoring, not self-declaration**: `pages/CompetitionJudgeEntry.tsx` (route `/competitions/judge-entry/:competitionId`, `allowedRoles={['admin','ouvreur']}`) is a grid (climbers × boulders) where a single judge enters everyone's top/zone/attempts — for blocs consécutifs sous le regard de tous, décidant d'un titre annuel, self-declaration doesn't carry the same weight it does in a casual 90-participant event. Writes to the exact same `competition_results` doc (`${uid}_${boulderId}_${competitionId}`) with the exact same debounce/flush/last-persisted pattern as `ClientCompetitions.tsx` — no schema change, no rules change (confirmed by `competition-results-lock.test.ts`: admin/ouvreur already have unconditional write access, including *creating* a result for a `user_id` that isn't their own). Locking is all-or-nothing (one "Verrouiller la finale" button batches `submitted:true` onto every participant at once), not per-climber — a deliberate simplification for a single-judge, single-sitting event. Reuses `applyCompetitionValidationUpdate` for the same input invariants as the client screen.
  - **A perfect tie at rank 1 resolves via a super-finale, not a shared title** (the user's call, 2026-08-16) — no dedicated code for this: the existing "add a boulder to a competition" flow (`CompetitionBoulderForm.tsx`/reusing a daily boulder) already lets an ouvreur add one more boulder to the same `competition_id` after the fact, and the judge enters results for just the tied climbers on it via the same grid — everyone else's totals are untouched since `getOfficialParticipantTotals` only accumulates from results that exist. The tie is visible to spot in the first place because both climbers already show rank 1 on the live display and in `CompetitionJudgeEntry.tsx`'s data.
  - A hand-computed 10-climber/5-boulder fixture, including a deliberate perfect tie at the top, is frozen as a test in `competitionClassement.test.ts` ("Finale de l'année") — the whole ranking is small enough to verify with a pencil, which is the strongest guarantee available at this scale.

Like `liveDisplayEnabled`, `scoring_mode`/`custom_scoring` are locked once a competition leaves `status: 'à venir'` — enforced **server-side** in `firestore.rules` (not just disabled in the UI), same `affectedKeys().hasAny([...])` pattern, same rationale: changing the mode mid-event would retroactively change everyone's score, not just future validations.

### Bloc Roulette — a free, stateless daily-challenge draw

`utils/roulette.ts` (V2.44, see `CONCEPTION-roulette-et-defis.md` Partie 1) draws one proposal from a fixed 46-entry catalog (`CATALOG`) plus a separate "roulette de la mort" entry, shown via a 🎲 button on `ClientDaily.tsx`. **The module imports nothing from Firestore** — that's the property that makes the feature free, called out in its own header comment and worth preserving on any future edit: the draw and "relancer" never cost a read or write. Everything it needs (today's active boulders, the climber's `level`, `wallCounts`) is already in memory or read as part of an existing `getDoc` call.

- **Level weighting**: `pickLevelTarget` picks max−1 (~70%), max (~20%), or max+1 (~10%) of the climber's current `users.level`; `resolveTargetColor` handles floor (max−1 collapses to the current level) and ceiling (max+1 collapses to max, flagging `levelExcludedE` so family E — "réussite partielle" — never appears once a climber is already at the top color). D and G aren't a separate weighting axis — once a tier is picked, every eligible family at that tier (including D/G) competes in one uniform draw.
- **Level-dedicated / level-shifted proposals (V2.55)**: `Proposal` carries optional `minLevel`/`maxLevel` (inclusive `Level` bounds) — `drawProposal` filters the tier pool through `levelAllows(userLevel, p)` before the uniform draw, with a safety net that ignores the restriction if it would empty the pool entirely at that tier. Also optional `levelOffset` (a number, e.g. `-1`): the entry still lives in its `levelTarget` pool, but the resolved `{couleur}` is shifted that many extra rungs down `levelOrder` — used by the "grimpe à une main" / "adhérences forcées" drills that deliberately target two rungs below (safety + the constraint alone makes them far harder). The V2.55 batch of exercises adapted from **al-escalade.fr**'s "bloc" discipline (B36–B46, C44, G43): touché-collé feet, no-foothold smearing, two-finger grip, imposed technique (cancan/lolotte/heel-hook/contrepointe/flag, each defined in `details`), one-handed (`levelOffset -1`), both-hands-together (`minLevel: rouge`), 6×40s resistance (`minLevel: rouge`), 3 linked boulders read aloud (`minLevel: bleu`), plus two advanced-technique entries gated at `minLevel: blanc` — Yaniro/figure-4 and bat-hang start, technique explained via `Proposal.details` (rendered under the label by `RouletteDialog.tsx`).
- **"Trouve un bloc du bon niveau, ou compose-en un" reminder (V2.55)**: shown once by `RouletteDialog.tsx` under every colour-targeted draw (hidden for a traversée) rather than repeated in each catalog string — same "say it once in the dialog" approach as the "Niveau visé" chip.
- **"J'ai relevé le défi" completion tracking (V2.55, "version hybride")**: a `RouletteDialog.tsx` button on **every** family (E and the death roulette included — decided 2026-09-06; it replaced the old family-E-only "C'est fait" button) fires `onValider`, whose `ClientDaily.tsx` `handleValiderRoulette` does **one** `updateDoc` on `users/{uid}`: `rouletteChallengesCompleted: increment(1)` + `rouletteRecentChallenges` (a client-recomposed, `ROULETTE_RECENT_COMPLETIONS_MAX`=10-capped array of `RouletteCompletion` via the pure `addRouletteCompletion`). **Never writes `client_boulder_results`** — so a family-E "un cran au-dessus" completion counts without touching classement/badges/level (the E invariant is specifically about not faking a boulder validation, not about never writing anything). **Zero extra reads**: the `users` doc is already fetched at ClientDaily mount (level/`wallCounts`), and the wall/boulder picker options are already in memory. The optional wall+number the climber may enter is stored on the entry (declared, unverified — same "confiance" doctrine as the declarative families). No new collection (rejected: an unbounded history query), no rules change (`rouletteChallengesCompleted`/`rouletteRecentChallenges` aren't locked keys), no reconciliation script (same rationale as `wallCounts`: private, playful, a drift is harmless). Counter shown under the roulette buttons on `ClientDaily.tsx` and, with the recent list, in `ClientStats.tsx` (both already read that `users` doc). `resolveDrawLabel(result)` (moved from `RouletteDialog` into `roulette.ts`, pure) resolves the stored label.
  - **No optimistic UI** (ClaudeNav review 2026-09-06): `handleValiderRoulette` updates `selfProfile` (the visible counter) **only after** `updateDoc` resolves — a failed write shows an error and leaves the counter untouched, never a count that ticks up next to an error message. `nextRecent` is recomposed from `selfProfileRef.current` (a ref synced in an effect, not the render-closure `selfProfile`) so two quick completions in one mount can't make the second overwrite the first in the 10-list; the count uses a functional `setSelfProfile(prev => …)`.
  - **⚠️ This counter is 100% declarative for every family** — even "un bloc à ton niveau" is never verified. It must **never become the input of anything derived** (a badge, a level bump, a classement contribution): a "10 défis Roulette relevés" badge would be self-awardable in ten clicks and would re-open, sideways, exactly what the family-E invariant closes. `rouletteChallengesCompleted` is display-only, forever.
  - **e2e**: `test/e2e-daily-flow.mjs` (steps 6–7) drives the button (incl. the optional wall/number field) and asserts `users.rouletteChallengesCompleted === 1` + the `rouletteRecentChallenges` entry via `firebase-admin` — per `PROCESSUS-erreurs-avalees.md` §4 ("every incremental counter needs an e2e assertion on its resulting value"), this being the project's **third** such counter after `colorCounts`/`wallCounts`.
- **`users/{uid}` is read in full by every staff screen** (`getDocs(collection(db, 'users'))`, unfiltered — `AdminUsers`, `CompetitionStats`, `AdminCompetitionStats`, `AdminCompetitionRegistration`, `BoulderStats`, `CompetitionBoulderStats`), and the client SDK has **no field projection**. Only put identity/rights fields there: name, role, level, date of birth, registrations. **Any per-user state — counters, preferences, display history — goes in `user_ludic_state/{uid}`**, read/written only by its owner (`services/ludicState.ts` is the only file that imports this collection, same discipline as `imageStorage.ts` for Cloudinary).

### Défis entre potes — a `challenges` collection, built on top of Bloc Roulette's counters

`utils/challenges.ts` (V2.46, `CONCEPTION-roulette-et-defis.md` Partie 2) is a small pure module (winner/progress logic only, no Firestore import, same discipline as `roulette.ts`) backing a `challenges/{id}` collection: 2–6 friends (`friendships`, accepted only — the UI in `ClientFriends.tsx` only offers already-accepted friends as participants, there is no separate invite/accept dance for a challenge itself) race on one of four `structure`s (`seuil`/`fenetre`/`bloc_designe`/`declaratif`). `progress` is a single map field on the document (`{uid: {value, updated_at, confirmed_by?}}`), never a subcollection — the 6-participant cap is what keeps Firestore's ~1 write/sec/doc contention limit a non-issue, see the conception doc §2.3; **never raise that cap without revisiting the model**.

- **No push notifications anywhere in this app** (confirmed while designing this feature — there's no FCM, no service-worker push): a challenge is discovered purely by pull, the next time a participant opens "Potes de grimpe" (`ClientFriends.tsx`, where the whole feature's UI lives — not a separate top-level tile, deliberately, since participant selection needs the friends list already loaded there). A creator's challenge appears with all participants already inside it (consent = being friends already), no per-challenge accept step.
- **Three structures update from `ClientDaily.tsx` automatically; `declaratif` is the only one with a manual write from `ClientFriends.tsx`** (a "C'est fait" button, one `updateDoc` on `progress.{uid}` only — no verification, consistent with the whole app's "confiance donnée aux grimpeurs" doctrine already established for the seasonal classement and Roulette).
- **Same incremental-counter discipline as `classement_profiles`/`wallCounts`**: active challenges (`status: 'en_cours'`, `participants array-contains uid`) are loaded **once** at `ClientDaily.tsx` mount (`activeChallengesRef`, `getDocsCacheFirst`) and kept in memory — never re-queried per validation. `pendingChallengeDeltaRef` (cumulative delta, for `seuil`/`fenetre`) and `pendingBlocDesigneScoreRef` (best-score-seen, for `bloc_designe` — a max, never a sum, since that structure compares a single best attempt on one designated boulder) are accumulated in `applyClassementDelta` alongside the pre-existing score/color/wall deltas, and flushed in the **same** debounced `runTransaction` as `classement_profiles`/`wallCounts` — one more reason that transaction now touches N+2 documents instead of 2.
- **`seuil` only counts a challenge's `target_color`** — which since V2.53 may be a literal colour *or* one of two per-participant tokens `SEUIL_TARGET_MAX` / `SEUIL_TARGET_MAX_MINUS_1` (`utils/challenges.ts`): `ClientDaily.tsx`'s seuil branch resolves it against **that grimpeur's own** `users.level` at delta time via `resolveSeuilTargetColor(target, level, levelOrder)` (pure, unit-tested), so two climbers of different levels can run a fair challenge (each counts blocs of their own max / max−1 colour). Floor: max−1 collapses to the current level at the bottom of `levelOrder`; unknown level → the challenge simply doesn't advance for that participant. `firestore.rules` doesn't validate `target_color` so no rules change was needed; `resolveSeuilWinner`/closure are unaffected (still a numeric `value` vs `target_count` compare). `fenetre` ignores color (metric `blocs`) or reuses the classement's own per-boulder `scoreDeltaForValidation` (metric `points`), gated on `now <= ends_at`; `bloc_designe` only reacts to its own exact `boulder_id` and only on success (a fail never lowers a previously-recorded best). None of the three ever re-reads another participant's `progress` entry — each participant's flush only touches its own key, exactly like `colorCounts`.
- **⚠️ Firestore transactions require every `tx.get()` before the first `tx.write()`/`tx.set()`, across the WHOLE transaction, not just per document** — found while building this feature's e2e test (2026-08-19): the pre-existing `wallCounts` write already violated this (`tx.get(userRef)` happened after `tx.set(ref, ...)` for `classement_profiles`), silently swallowed by the transaction's own `catch` block ever since V2.44 (`wallCounts` may have been silently failing to update in prod since then — never visibly broken because nothing surfaces that failure to a user, and no e2e test previously exercised the wall-delta path with assertions on the write's outcome). Fixed alongside this chantier by regrouping every `tx.get()` (classement_profiles, users/wallCounts, every touched challenge doc) before any `tx.set()` in `flushClassementWrite`. Any future addition to that transaction must preserve this "reads, then writes" ordering.
- **Closure is a pull-only action, no cron**: `fenetre` auto-closes itself — any participant who opens `ClientFriends.tsx` after `ends_at` has passed triggers a `useEffect` that computes the winner (`resolveFenetreWinner`) and writes `status: 'termine'`/`winner_uid` right then, first-to-open wins the race (harmless — same result either way). `seuil`/`bloc_designe` show a "Clôturer" button once a winner is computable, clickable by **any** participant (not just the creator — user's call, 2026-08-19); `declaratif` has no computed winner, just a manual "Terminer le défi" button. Firestore rules enforce closure as one-shot and field-scoped: an update may touch `progress` (and only the caller's own key within it, checked via a **nested** `diff()` — `request.resource.data.progress.diff(resource.data.progress).affectedKeys()`, not just the document-level `diff()`) **or** `status`+`winner_uid` transitioning `en_cours` → `termine`, never both in the same write, never re-opening a closed challenge.
- **Deletion (V2.53)**: the creator (`created_by`) may `delete` their own challenge from `ClientFriends.tsx` ("Supprimer ce défi", `window.confirm`), any status — for pulling a test/abandoned challenge. `firestore.rules` `allow delete: if resource.data.created_by == request.auth.uid`. Safe mid-flight: `ClientDaily.tsx` loads active challenges once at mount and `buildClassementFlushWrites` already skips a vanished challenge (`if (!challengeData || !challengeRef) return;`).
- **No reconciliation script** for `challenges`, unlike `colorCounts`/`wallCounts`'s siblings — same rationale as `wallCounts`: low stakes, short-lived documents, a drift disappears when the challenge ends. Deliberate, not an oversight.
- Tests: `utils/challenges.test.ts` (pure logic — winner resolution incl. ties, progress deltas incl. removal), `test/firestore.rules.test.ts` (`describe('challenges...')` — create bounds, read/write scoping, closure lock), `test/e2e-challenges-flow.mjs` + `test/seed-challenges-users.mjs` (real browser, `seuil` end-to-end incl. auto-updating from `ClientDaily.tsx`, plus `declaratif`'s manual button) — run manually against local emulators + `vite --port 5174` per the project's existing e2e convention (no npm script wires this in, see Testing section below). **When validating two boulders back-to-back in an e2e script, stay on the same page/mount and wait out the debounce rather than navigating between them** — a `pagehide`-triggered flush is not guaranteed to complete before a real browser navigation tears down the page (no `sendBeacon`/keepalive behind a Firestore transaction), so a hard navigation mid-flush is a flaky way to force a write in a test, even though it's the right mechanism for the app's real "closing the tab" case.

### Badges (`badges` catalog / `client_badges` links) — manual by moniteur, plus auto colour badges since V2.53

`badges` is a small hand-curated catalog. `client_badges/{uid}_{badgeId}` links a badge to an account; once created it's immutable (`update, delete: if false` in `firestore.rules`). `ClientStats.tsx` reads these and `utils/badgeActivation.ts`'s `computeBadgeActive` decides live whether each owned badge shows coloured or greyed (does the client still have ≥ `criteria.count` validated boulders of that colour that still exist **as an active daily boulder** in the gym — `"all"` means every active daily rose in the gym, the "master" badge). The client's `level` is then synced to the highest active badge colour unless `levelOverride` is set.

- **Manual badges** (legacy four `badge-debutant`/`-intermediaire`/… with a free-text `criteria` string, plus diplomas) are awarded only by a moniteur in `Moniteur/Stats/StatsList.tsx` (`awardBadgeToUser`, non-deterministic doc id `${uid}_${badgeId}_${Date.now()}`).
- **Automatic colour badges** (`type: "automatic"` in the catalog — Earl/Duke/Prince/King/Emperor `violet/rouge/noir/blanc/rose` = "réussir un bloc <colour>", plus Master `rose` with `criteria.count: "all"`): **nothing awarded these before V2.53** (found once the app went public — a colleague validated boulders and got no badge). Now `ClientStats.tsx`'s `fetchStats`, right before the level sync, walks the catalog and for every `type:"automatic"` badge the client doesn't already own whose `computeBadgeActive` is true, writes `client_badges/${uid}_${badgeId}` (deterministic id → no dupes on reload) with `awardedBy: "auto"`. Retroactive by construction: any account gets its due badges next time it opens "Mes stats". `firestore.rules` `client_badges` `create` is correspondingly widened: a plain client may create **only** a doc for its own uid, `awardedBy == "auto"`, canonical id `uid_badgeId`, exactly those 5 keys, and only if `badges/{badgeId}` exists with `type == "automatic"` (`get()` in rules). Still immutable afterward. Rules tests: `test/firestore.rules.test.ts` `describe('client_badges : auto-attribution…')`. In prod every non-master colour badge has `criteria.count: "1"` (a string — `computeBadgeActive` reads it via `parseInt`, default `1` when absent); the read-only `firestore-migration/audit-badges-criteria.js` re-verifies that invariant against the live catalog.

#### Badge "mise en veille" on wall rotation, and its knock-on to `users.level` / `users.baseLevel` (V2.54)

The greying is not cosmetic — it feeds a chain: greyed badge → `computeBadgeActive` false → level sync drops `users.level` → seuil-challenge `SEUIL_TARGET_MAX` target, Bloc Roulette calibration, "niveau max" displays all shift. So the exact "still in the gym" test matters.

- **What counts for a badge / the level sync** (`ClientStats.tsx`, `fetchStats`): a validated boulder only keeps its colour badge lit if its `boulders` doc is still `is_active === true && type === 'daily'` (`countsForBadges` flag in the per-result loop). A wall rotation never deletes boulder docs — `DailyBoulderForm.tsx` only sets `is_active: false` — so a pure `boulderDoc.exists()` check (the pre-V2.54 behaviour) meant a colour badge **never** greyed. The "master" denominator (`inventoryByColor`) is now a filtered query `boulders where type=='daily' && is_active==true` (same composite index ClientDaily.tsx already uses — no `firestore.indexes.json` change) instead of a full-collection read, so deactivated/competition boulders no longer inflate the `"all"` target. This also makes that read bounded (active daily inventory) instead of growing forever with every retired boulder.
- **`baseLevel` = niveau *déclaré*, `level` = niveau *constaté*.** Colour badges start at `violet` (nothing for `jaune/vert/bleu`). While **at least one** colour badge is active, `level` follows the highest active badge colour and `baseLevel` has no effect. When **no** colour badge is active but `level >= violet`, the `ClientStats.tsx` level sync writes `level` back to `baseLevel` (or `'bleu'` as the default for legacy accounts with no snapshot — "you probably declared bleu"), **never upward**. `baseLevel` is written by: `Register.tsx` (at registration), `ClientProfile.tsx` (V2.54.1 — saving the profile is a re-declaration: it writes `baseLevel` alongside `level`, so the sync respects the new value instead of clobbering it with a months-old snapshot — the exact bug of the returning-injured-climber case), and the level sync itself as a one-time snapshot for legacy accounts that have neither (`!userData.baseLevel && currentLevelIndex < colorOrder.indexOf('violet')`). `baseLevel` is not a locked key in `firestore.rules` (locked: `inscritAuxCours`/`inscritAuxCompetitions`/`role`/`roles`/`levelOverride`), so the client writes it to their own doc with no rules change. The `ClientProfile.tsx` level field carries a caption saying it only takes effect when all badges are dormant. Cost unchanged: still at most one `updateDoc` on `users` per "Mes stats" open, occasionally carrying a second field.
- **A level drop cannot break a running challenge.** `seuil` compares a numeric cumulative `progress[uid].value` against a fixed `target_count`; the level only decides *which future validations* increment it (`resolveSeuilTargetColor` in `ClientDaily.tsx`, re-read from `users.level` at each `ClientDaily` mount). Existing progress is never recomputed or decreased, and `resolveSeuilWinner` stays a pure `value >= targetCount`. `fenetre`/`bloc_designe`/`declaratif` targets don't depend on level at all.
- Read-time explanation for the user (so a greyed badge reads as an objective, not a bug): the inactive-badge `Chip` in `ClientStats.tsx` ("Badge en veille : … Il se rallume dès que vous en revalidez un"), a line in `ClientHelp.tsx` ("Mes statistiques" section), and a `changelog.ts` V2.54 entry announcing the one-time mass greying of long-retired walls as a deliberate choice.

### First ascents (`boulders/{id}.firstAscents`) — a capped list, not a counter, V2.61

`PLAN-premiers-ascensionnistes.md`: on a hard-colour boulder (`gymConfig.firstAscentColors`, currently `['noir', 'blanc', 'rose']`), the first five climbers to validate it are shown on its detail card, in order, with their first-validation date. **Cost: ~0 extra reads, ≤5 writes per boulder over its whole life** — the list lives directly on the boulder document (`boulders/{id}.firstAscents: {uid, displayName, at}[]`), already loaded by `ClientDaily.tsx`; querying `client_boulder_results` instead was rejected outright (blocked by rules — a client can't read another client's results, that's the whole reason `classement_profiles` exists) and a `boulders/{id}/first_ascents/{uid}` subcollection was the fallback if the rule below turned out infeasible (5 reads per card open instead of 0).

- **Consent is a dedicated field, not `classementOptIn`** — `firstAscentOptIn: boolean` (default `false`), stored in `user_ludic_state/{uid}` (the ludic-state migration above was already in flight when this was built, so it went straight to the new collection rather than adding another line to `users`), toggled in `ClientProfile.tsx`. Evaluated only at validation time — enabling it later never backfills past validations, and the UI says so.
- **Firestore rules enforce append-only integrity, not just size** — the naive approach (`request.resource.data.firstAscents == resource.data.firstAscents + [newEntry]`) does **not work**: Firestore's rules language has no list concatenation operator (`"Unsupported operation error: list + list"`, confirmed on the emulator — a real dead end, not a hypothetical one). The working alternative, `isAppendOnly4()` in `firestore.rules`, unrolls the comparison into up to 4 individual indexed equality checks (`newList[0] == oldList[0]`, …) — since the list is capped at 5, the existing prefix before any single write is at most 4 elements long. This is what makes the list **actually tamper-proof**: a client can add their own entry at the end, but cannot rewrite, reorder, or drop any earlier entry, cannot add another uid's entry, and cannot write once the list already has 5. Add a 5th unrolled index (and bump the cap check) if `FIRST_ASCENT_LIST_MAX` ever changes. A client update is also confined to `type == 'daily' && !competition_active` (never on a hidden-cotation competition boulder — see the boulders lifecycle section above) and `diff().affectedKeys().hasOnly(['firstAscents'])`; staff (ouvreur/admin) keep unrestricted write access, unchanged.
- **The write is immediate, never debounced** — triggered by the "Réussi" click, already immediate, and happens at most once per boulder per climber. It does **not** share `ClientDaily.tsx`'s debounced classement/wallCounts/challenges transaction; it's its own small `runReadThenWriteTransaction` (`utils/firstAscentWrites.ts`'s `buildFirstAscentWrite`, pure, same "reads before writes" discipline as `classementFlushWrites.ts`) that re-reads the boulder doc fresh at write time — never the boulder's in-memory copy in `ClientDaily.tsx` state, which could be stale if another climber just took the 5th spot. `shouldRecordFirstAscent()` (`utils/firstAscents.ts`, pure, unit-tested) centralizes the six preconditions (success, opt-in, eligible colour, `type:'daily'` non-competition, list not full, uid not already present); a failure here is caught and logged to console only — the boulder validation itself already succeeded by this point, and missing a prestige-list slot must never surface as a user-facing error on an otherwise-successful validation.
- **Withdrawal isn't retroactive by itself**: turning `firstAscentOptIn` off doesn't remove a name from lists it's already on (frozen in each boulder doc, nothing scans the whole collection to find it). `scripts/purge-first-ascent-entry.js` (dry-run by default, `--fix`, requires `--uid`) removes every occurrence of a given uid on explicit request — on-demand only, no cron, since there's no periodic drift to correct here, only an occasional real request.
- **A deactivated boulder keeps its list** — consistent with the project's "never delete a `boulders` doc" invariant (V2.56): the list becomes a small standing "palmarès" of a retired wall rather than disappearing with it, at zero extra cost since the document was never going away anyway.
- Verified end-to-end against the emulator, not just via rules tests: `test/e2e-first-ascents-flow.mjs` + `test/seed-first-ascents-users.mjs` — two real climbers filling a boulder's list from 3/5 to 5/5 in order, then a third climber validating on a full list, asserting the write is silently rejected (their own boulder validation still succeeds) and the list stays untouched. This is the one property that bounds the whole feature's cost, hence the one locked by a test.

### Weekly goals (`ClientScreen.tsx`) — cumulable since V2.52, computed live, never persisted as a counter

`users/{uid}.weeklyGoalItems: WeeklyGoalItem[]` (introduced V2.52, `utils/weeklyGoal.ts`) replaces the earlier single `weeklyGoalTarget: number` ("N blocs, tous niveaux confondus") with a **cumulable list** of goals for the current week (Monday to today): `{type:'color', color, target}` (e.g. "2 rouges"), `{type:'boulder', boulderId, boulderLabel}` (a specific boulder, e.g. "bloc n°6 - Dalle"), or `{type:'all', target}` (the old behavior, kept as one selectable goal type among others, not removed). Items are freely combinable in one list (e.g. 2 rouges + 3 noirs + one specific boulder), capped at `MAX_WEEKLY_GOAL_ITEMS` (8).

- **`utils/weeklyGoal.ts` is a pure module, no Firestore import** — same discipline as `roulette.ts`/`challenges.ts`. `computeWeeklyGoalProgress(items, validationsThisWeek, colorById)` returns per-item `{current, target, done}`; `upsertGoalItem` replaces (never duplicates) an existing item of the same kind (same color, same boulderId, or the single `'all'` item) when the user adds another one like it — avoids the ambiguity of two "rouge" goals in the same list. Unit-tested in isolation (`weeklyGoal.test.ts`), no emulator needed.
- **Progress is recomputed live on every page load, exactly like the pre-V2.52 design — deliberately not an incremental counter** (unlike `classement_profiles`/`wallCounts`/`challenges.progress`): `ClientScreen.tsx` already read all of the user's own `client_boulder_results` (success:true) once per mount for the streak feature: the same read now also carries `boulderId`, filtered to this week, and is joined against a lazily-loaded `colorById` map (`boulders` where `type=='daily' && is_active==true`, fetched only when at least one `'color'`-type goal exists — a `'boulder'`/`'all'`-only goal list costs zero extra reads). This is a personal, low-stakes, cheap-to-recompute stat — same rationale as `wallCounts` having no reconciliation script.
- **Same "createdAt this week" semantics for all three goal types, including `'boulder'`, by deliberate choice**: `client_boulder_results.createdAt` is immutable after first success (see below); a goal is "done" when a boulder's (or a color's) **first-ever** success falls within the current week's window, not merely re-validated this week. For a `'boulder'` goal this means picking an already-long-validated boulder as this week's goal is honestly shown as not-done-this-week rather than trivially satisfied — consistent with `'color'`/`'all'`, not a special case.
- **Legacy read-time fallback, same pattern as `legacyAge`/`image_base64`**: `legacyGoalToItems(weeklyGoalTarget)` converts an old-shaped `weeklyGoalTarget` number into a single-item `[{type:'all', target}]` at read time for accounts that set a goal before V2.52 — `weeklyGoalTarget` is never written again; the first time a user saves from the new dialog, it's cleared via `deleteField()` and `weeklyGoalItems` takes over as the only field going forward.

### Swallowed-error process (`PROCESSUS-erreurs-avalees.md`, V2.47 → V2.49, now complete)

Written by ClaudeNav straight after the V2.46 transaction bug above — not about that one bug (already fixed) but the *class* of bug it represents: a permanent, deterministic failure disguised as a retryable transient one, silently swallowed by a `catch` that just re-queues and never surfaces. Four steps; §1/§2/§4 landed in V2.47, §3 (the structural refactor) in V2.48 as its own dedicated version, per the document's explicit warning not to mix it with the others — it touches three production write paths that had each already been the site of a real data-loss fix once before.

- **§1 (inventory via ESLint, report mode)**: `eslint.config.js` sets `@typescript-eslint/no-unused-vars` with `caughtErrors: 'all'` and `no-empty` with `allowEmptyCatch: false`, both at `'warn'` (not `'error'`) — deliberately non-blocking until the existing surface is fully triaged. **Result: zero findings** — every `catch` in the codebase already reads its error variable in some form, so this heuristic didn't catch the V2.46 bug and wouldn't have; it exists for the empty/no-op case, not the "logged once, retried forever" case that actually happened. Still `'warn'`, not flipped to `'error'` — that flip is its own separate, still-open step (§6 of the document), not bundled into §3.
- **§2 niveau 1 (console.error everywhere)**: audited every debounced-flush write path — `console.error` added to `ClientCompetitions.tsx`/`ClientCourseSession.tsx`'s catches (they already had user-facing `setError`, just missing the console trace for the screenshot-diagnosis case CLAUDE.md's own testing conventions rely on).
- **§4 (assert the effect, not just "didn't crash")**: `e2e-daily-flow.mjs` gained a direct backend assertion (`firebase-admin`, bypassing rules) on `users.wallCounts` after a validation — the exact counter the V2.46 bug had silently broken, and the concrete reason this e2e never caught it: it asserted the classement was right but never checked `wallCounts` at all. `season.*`/`classement_profiles` were already asserted this way in `e2e-season-classement-flow.mjs`. `challenges.progress` remains covered for `seuil`/`declaratif` only, not `fenetre`/`bloc_designe` — pre-existing gap, unchanged, see `HANDOFF-defis-entre-potes-2026-08-19.md`.
- **§3, part A — the transaction helper (`utils/firestoreTransaction.ts`)**: `runReadThenWriteTransaction(db, reads, buildWrites)` takes a flat `Record<string, DocumentReference>` of everything to read and a **pure** `buildWrites(readData) => TransactionWrite[]` function — `buildWrites` never receives `tx` itself, so it is *structurally* impossible for it to call `tx.get()` after a write; the helper does every read (in key order) before calling `buildWrites` and applying its writes. `ClientDaily.tsx`'s `flushClassementWrite` is the only caller today (`classement_profiles`/`users.wallCounts`/`challenges.progress`, the exact transaction that had the V2.46 bug) — its write-building logic was extracted into `utils/classementFlushWrites.ts`'s `buildClassementFlushWrites`, now a plain function with **no Firestore import**, unit-tested (`classementFlushWrites.test.ts`, 12 cases) without an emulator — the "bénéfice secondaire" the document predicted.
- **§3, part B — one debounced-flush hook (`utils/useDebouncedFlushQueue.ts`)**: replaces three separate hand-rolled implementations (`ClientDaily.tsx`, `ClientCompetitions.tsx`, `ClientCourseSession.tsx` — the document counted the défis path as a fourth, but its writes already shared `ClientDaily`'s single transaction, so there were only three distinct implementations, not four) that each had their own timer bookkeeping, their own technique against a stale `pagehide` closure (a ref-of-closure here, a `useCallback` dependency list there, a dependency-less effect elsewhere — now just one), and their own ad hoc catch. The hook is generic over a per-key payload `T` and a caller-supplied `merge(older, newer) => T`: **accumulate** semantics (`ClientDaily`'s classement delta — `mergeClassementFlushPending`, additive) and **replace** semantics (`ClientCompetitions`/`ClientCourseSession`'s per-boulder/per-exercise validation snapshot — `(_older, newer) => newer`) both fit the same contract; the hook always **re-queues on failure** using that same `merge`, a small robustness upgrade for the two "replace" screens (they used to silently drop a failed write with no retry at all). Console logging, the failure counter (§2 niveau 2), and escalation to a caller-supplied `onDurableFailure`/`onRecovered` (§2 niveau 3, reusing each screen's existing `error`/`Alert` state, never a new `Snackbar`) are now inside the hook, not copy-pasted per screen. `ClientCompetitions`/`ClientCourseSession` keep `failureThreshold: 1` (they already surfaced every failure immediately, stronger than `ClientDaily`'s tolerance for a transient blip, commented at each call site so nobody "helpfully" aligns them later) plus a new `onRecovered` clearing the error on the next success.
  - ⚠️ **The `merge` contract's argument order is `(older, newer)`, never `(prev, incoming)`** — found by ClaudeNav's review the same day this shipped (V2.50). The hook calls `merge` from two places with an *opposite* freshness relationship: in `enqueue()`, what's already queued is older than the arriving payload; in the failure-retry path, the payload that just failed is older than whatever got enqueued during the failed `await`. A naive `merge(prev, incoming)` that special-cased "prev wins if it exists" (right for the retry case) was silently *wrong* for the enqueue case — two rapid edits within one debounce window (e.g. essais 2 then 3) would persist the **first** value, not the last, because "prev" in that call is the older one. The additive case never exposed this (addition is commutative, order doesn't matter — which is exactly why it shipped unnoticed). Fixed by making the hook itself respect strict age ordering at both call sites and only ever handing `merge` two arguments it's already labeled `(older, newer)`; the undefined-on-one-side cases (nothing queued yet / nothing newer since the failure) are handled by a separate pure `combineByFreshness` helper before `merge` is even called, so `merge` itself only ever sees two real values. `combineByFreshness` is exported and unit-tested (`useDebouncedFlushQueue.test.ts`) — including the exact "essais 2 then 3" scenario — the one piece of this hook that *can* be verified without a React test harness, and the one that actually would have caught this.
- **Verification for §3**: the existing e2e suite was the filet, exactly as the document asked — `e2e-daily-flow.mjs` (wallCounts assertion), `e2e-challenges-flow.mjs`, `e2e-season-classement-flow.mjs` (all three exercising `ClientDaily`'s migrated transaction), `e2e-competition-flow.mjs` (`ClientCompetitions`), `e2e-course-flow.mjs` (`ClientCourseSession`'s exercise queue). 59 e2e steps green, no regression, alongside the full `npm test`/`npm run test:rules` suite.
- **§1/§6 closed in V2.49**: `e2e-course-minicompetition-flow.mjs` + `seed-course-minicompetition.mjs` close the one flagged gap — `ClientCourseSession.tsx`'s *other* queue (`boulderQueue`, mini-compétition results, distinct from the exercise queue `e2e-course-flow.mjs` already covered) now has its own dedicated 10-step e2e (immediate write on "Réussi", debounced `enqueue` on the essais `Select`, a direct `firebase-admin` assertion on the written `client_course_results` doc, survival across a reload, the final "Enregistrer" `writeNow`, and the archived read-only view). Same run also flipped `eslint.config.js`'s `@typescript-eslint/no-unused-vars`/`no-empty` from `'warn'` to `'error'` — the inventory was still zero, so this was a pure formality, not a fix.

### App version display

`frontend/package.json`'s `version` field is the single source of truth for the version number shown to users (a `VX.XX` caption in the Navbar, next to the gym logo — `components/Navbar.tsx`, visible on every page; moved there in V2.40 from a caption under the title on "Mon espace personnel" to stop lengthening that screen's mobile scroll) — `vite.config.ts` reads it at build time and injects it as the `__APP_VERSION__` global (declared in `src/vite-env.d.ts`, formatted in `src/config/appVersion.ts`). This exists so a user can tell whether their PWA actually loaded the latest deploy or is still serving a stale service-worker-cached build — bump `package.json`'s `version` to match whatever version number is used in the commit message (the pre-existing "Application Sociale Blocabrac V2.XX" convention in git history) whenever asked to tag a release; it takes effect on the next build/deploy, no other step needed.

### Visual identity: matches the gym's real website (`www.blocabrac.fr`)

V2.40 aligned the MUI theme with the gym's actual public website instead of MUI's default blue/Roboto: primary color `#27B142` (dark variant `#177038`, both in `config/gymConfig.ts` as `brandGreen`/`brandGreenDark`) and the "Dosis" font, both read directly from that site's live CSS — set once in `context/ThemeModeContext.tsx`'s single `createTheme(...)` call (`palette.primary`, `typography.fontFamily`), so it propagates to every button/link/focus ring/AppBar without touching individual screens. `VITE_THEME_COLOR` in `.env` (browser chrome tint + PWA manifest icon backdrop) was updated to the same green — it does **not** feed the MUI theme itself, that's a separate `env.VITE_THEME_COLOR` read only in `vite.config.ts`'s PWA manifest block, so both must be kept in sync by hand if the brand color ever changes again. Dosis is self-hosted (`src/assets/fonts/dosis-variable-latin.woff2`, one variable-weight file covering 200–800, `src/styles/fonts.css`'s single `@font-face`, imported from `main.tsx`) rather than linked from `fonts.googleapis.com` — this app's PWA app-shell is meant to survive being reopened offline (see IndexedDB/service-worker section above), and a third-party font request would fail offline and delay first paint online; `vite.config.ts`'s workbox `globPatterns` includes `woff2` so the font file itself is precached like the rest of the shell. The "latin" Google Fonts subset (`U+0000-00FF`) is sufficient — it already covers every accented character French needs (é/è/à/ç/ù/etc.), no need for `latin-ext`. The one other pre-existing hardcoded color (a blue/purple gradient on the shareable progress card, `Client/ClientScreen.tsx`) was repainted to the same green pair for consistency — it was the only other spot in the app not already driven by the MUI theme.

**PWA icons (`frontend/public/icons/`) — version the filename, never the content (V2.58)**: the three icons (`pwa-192x192-v2.png`, `pwa-512x512-v2.png`, `maskable-512x512-v2.png`) are white symbol on `#27B142`, derived from `src/assets/logo-blocabrac.png` (lettering/grain stripped, maskable safe zone respected). Files in `public/` carry **no build hash** — the service worker precaches them by name, so replacing an icon under its existing filename is exactly the case that stays stuck in cache. Any icon change must land under a **new `-vN` filename**, delete the old one, and update the `icons` array in `vite.config.ts` + the `apple-touch-icon` in `index.html` (grep `pwa-192`/`pwa-512`/`maskable` to be sure nothing else points at the old name). The manifest's `background_color` (PWA splash screen) is set to `env.VITE_THEME_COLOR`, same as `theme_color` — keep them equal. Note: an already-installed PWA keeps its old icon until reinstalled — OS behaviour, nothing to code.

### Testing

- `npm test` (fast, no external deps) covers pure utility functions (`utils/*.test.ts`) — this is what CI-equivalent checks should always run.
- `npm run test:rules` (Firestore emulator, `frontend/test/*.test.ts`) is the only way to verify Firestore security rules and cross-collection permission logic (e.g. `canValidateCourse`, role checks). Any change touching `firestore.rules` or a write path's field shape should get a test here, following the existing pattern: `initializeTestEnvironment` + `withSecurityRulesDisabled` to seed fixtures, then `assertSucceeds`/`assertFails` against role-specific `authenticatedContext`s.
- There is no Playwright/browser E2E suite wired into these npm scripts, despite `playwright` being a devDependency — manual/agent-driven browser testing is done ad hoc, not via a committed test suite.
